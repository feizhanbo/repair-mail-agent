## §1 项目概述

**项目名称**：repair-mail-agent — 邮件报修自动化系统

**业务定位**：面向 Accotest 客户邮件报修场景的自动化处理系统，目标是在三个月内完成可内部试运行的闭环。

**核心业务流程**：

```text
邮件接收 → 原文归档 → 回复链识别 → 模板/附件解析 → AI 辅助判断
→ SN 校验 → 自动追问/人工复核 → 工单沉淀 → 可导出
```

**系统目标**：

1. 从报修邮箱自动拉取客户邮件，保存原始 EML、邮件正文、HTML、邮件头、附件元数据和 OSS 对象引用。
2. 识别新报修、客户补充、内部转发、无关邮件和无法判断邮件。
3. 支持标准模板、正文自由文本、历史回复链、Excel/TXT/PDF/DOCX/图片附件中的报修信息提取。
4. 以 SN/资产校验库判断 SN 是否存在、有效、与客户及物料匹配。
5. 缺失关键信息时生成追问草稿，默认必须人工审核后发送。
6. 低置信度、SN 异常、字段冲突、追问超限、系统异常进入人工复核队列。
7. 控制台可追溯邮件原文、附件、解析候选、AI 摘要、SN 校验、状态流转和人工修改记录。

**一期范围**：

- 后端 FastAPI 服务、数据库迁移（26 张表）、API、后台任务、日志审计。
- 前端 React 控制台、登录鉴权、核心业务页面和通知能力。
- MySQL 8.x 数据库。
- IMAP 收信、SMTP 发信（默认关闭真实自动发送）。
- 阿里云 OSS 文件存储。
- APScheduler 轻量任务调度。
- AI Provider 抽象层：支持 DeepSeek 与 Qwen 双 Provider。
- Docker Compose + Nginx + GitHub Actions 部署。

**一期不做**：

- SAP/IT 中转服务器真实对接。
- 多邮箱账号控制台维护。
- 独立客户主数据体系。
- 企业微信、邮件、Webhook 等外部通知集成。
- 高可用集群、复杂分布式任务队列、多租户权限体系。

## §5 AI Provider 架构

### §5.1 Multi-Provider 支持

系统当前支持 **双 AI Provider**：DeepSeek 和 Qwen，均可用于生产环境。

| Provider | 文件 | 能力 | 配置 |
| --- | --- | --- | --- |
| `DeepSeekProvider` | `integrations/ai_provider.py` | `chat_json()` 文本 JSON 结构化输出 | `AI_API_KEY`, `AI_MODEL`, `AI_BASE_URL` |
| `QwenProvider` | `integrations/qwen_provider.py` | `chat_json()` 文本调用 + `vl_chat()` 多模态调用（图片/PDF） | `QWEN_API_KEY`, `QWEN_MODEL`, `QWEN_BASE_URL` |

**Provider 选择逻辑**（`app/services/ai.py` → `_provider()`）：

```python
if settings.AI_PROVIDER.lower() == "qwen":
    return QwenProvider(...)
return DeepSeekProvider(...)
```

**ai_configured() 双判断**：

```python
def ai_configured() -> bool:
    return (settings.AI_PROVIDER.lower() == "deepseek" and bool(settings.AI_API_KEY)) or \
           (settings.AI_PROVIDER.lower() == "qwen" and bool(settings.QWEN_API_KEY)) or \
           bool(settings.AI_API_KEY)
```

### §5.2 重试机制

`_run_ai_json()` 调用入口实现指数退避重试：

- `AI_MAX_RETRIES=2`（共 3 次调用机会）
- 退避延迟：`AI_RETRY_BASE_DELAY_SECONDS * (2 ^ attempt)`，即第 1 次重试等 1.0s，第 2 次等 2.0s
- 可重试错误类型：TIMEOUT、OUTPUT_NOT_JSON、OUTPUT_SCHEMA_INVALID、HTTP 5xx
- 不可重试错误：HTTP 4xx、其他非临时性错误

### §5.3 多模态解析

当使用 Qwen Provider 时，`parse_attachment_multimodal()` 调用 `vl_chat()` 接口对图片（image/*）和 PDF 附件进行视觉识别。此功能仅在 `QWEN_API_KEY` 已配置时可用。

## §6 SMTP 收件人白名单

### §6.1 三层拦截机制

为防止开发/测试阶段误向真实客户邮箱发送邮件，系统实现了 **SMTP 收件人白名单三层拦截**：

| 层级 | 函数/位置 | 行为 |
| --- | --- | --- |
| 第一层 | `create_reply_draft()` | 草稿生成后，若收件人不在白名单 → 强制 `review_status=pending` + 警告日志 |
| 第二层 | `_reply_can_auto_send()` | 自动发送条件检查，白名单外 → 拒绝自动发送 |
| 第三层 | `_send_reply_via_smtp()` | SMTP 发送前最终检查，白名单外 → 直接返回 "收件人邮箱不在白名单中，开发阶段禁止向真实客户邮箱发信。" |

### §6.2 白名单配置

```python
SMTP_RECIPIENT_WHITELIST=["rmatest2@accotest.com"]
```

当白名单为空时，系统启动时记录 SECURITY 级别警告日志："SMTP_RECIPIENT_WHITELIST is empty, all outbound email will be blocked!"

## §7 后台任务调度

### §7.1 APScheduler 初始化

`app/main.py` 在应用 `lifespan` 中初始化 `AsyncIOScheduler`，注册两个定时 Job：

| Job ID | 调度间隔 | 配置项 | 函数 | 说明 |
| --- | --- | --- | --- | --- |
| `imap_poll` | 每 5 分钟 | `IMAP_POLL_INTERVAL_MINUTES` | `_scheduled_imap_fetch()` | 从 IMAP 拉取新邮件，写入 `mail_fetch_records` |
| `auto_followup` | 每 5 分钟 | `AUTO_FOLLOWUP_INTERVAL_MINUTES` | `_scheduled_auto_followup()` | 扫描 `need_customer_info` 工单，自动生成追问草稿 |

### §7.2 自动追问逻辑

1. 查询所有 `current_status_code=need_customer_info` 的 `repair_tickets`。
2. 跳过 `followup_count >= max_followup_count` 的工单。
3. `AUTO_SEND_ENABLED=false` 时全部跳过（当前默认行为）。
4. 对每个符合条件的工单调用 `create_reply_draft()`，生成草稿并创建人工审核任务。

## §9 工单状态机

### §9.1 状态定义

| 状态码 | 含义 | 前端颜色 |
| --- | --- | --- |
| `new_email` | 新邮件入库，尚未解析 | 蓝色 |
| `parsed` | 已完成解析 | 青色 |
| `need_customer_info` | 缺失关键信息，需追问客户 | 橙色 |
| `auto_replied` | 已生成/发送追问草稿 | 紫色 |
| `manual_review` | 进入人工复核 | 红色 |
| `ready_for_export` | 信息完整、可导出 | 绿色 |
| `error` | 系统异常 | 红色 |
| `closed` | 已关闭 | 灰色 |

### §9.2 主要流转

```text
new_email → parsed → ready_for_export          (信息完整、SN 校验通过)
new_email → parsed → need_customer_info        (缺关键字段)
need_customer_info → auto_replied              (生成追问草稿)
auto_replied → parsed                          (客户回复补充信息)
任意非终态 → manual_review                     (低置信度/SN异常/冲突/超限)
manual_review → ready_for_export               (人工修正通过)
任意非终态 → error                              (系统异常)
任意非终态 → closed                             (人工关闭)
```

状态流转由 `workflow_transitions` 表定义，通过 `transition_ticket()` 执行，每次流转写 `ticket_status_logs`。

## §13 部署架构

```text
用户浏览器
    │
    ▼
Nginx (80/443)
    │
    ├── /api/* ──────► backend (FastAPI, 8000)
    │                      │
    │                      ├── MySQL (3306)
    │                      ├── 阿里云 OSS
    │                      ├── IMAP/SMTP 服务器
    │                      └── AI API (DeepSeek / Qwen)
    │
    └── /* ──────────► frontend (static files, 5173)
```

- Docker Compose 管理所有服务。
- GitHub Actions 自动部署。
- 配置文件通过 `.env` 和 CI/CD Secrets 注入。
- 禁止手动在生产环境直接修改代码。
- 所有服务可重建，业务服务无状态，文件入 OSS，持久数据入 MySQL。

## §14 关键默认决策汇总

| 决策项 | 默认值 | 说明 |
| --- | --- | --- |
| 一期数据库表数 | 26 | 不含后续扩展表 |
| 自动回复模式 | `human_review` | 默认只生成草稿并人工审核 |
| 自动发送开关 | `AUTO_SEND_ENABLED=false` | 默认关闭 AI 自动发送 |

| AI 最大重试 | `AI_MAX_RETRIES=2` | 指数退避重试 |
| AI 置信度阈值 | `CONFIDENCE_THRESHOLD=0.7` | 低于阈值进入人工复核 |
| SAP/IT 中转 | 不真实对接 | 只保留导出边界 |
| 客户主数据 | 不建设独立表 | 从邮件解析和 SN 库获取 |
| AI 详细日志 | JSONL 文件 | 数据库只保存摘要索引 |
| 附件和 EML | OSS 存储 | 数据库不存二进制 |
