# 邮件报修自动化系统 — 开发指导文档

生成日期：2026-07-12

## §1 项目定位与一期边界

### 1.1 项目定位

邮件报修自动化系统（`repair-mail-agent`）是一套面向内部试运行的邮件报修处理控制台。系统通过 IMAP 自动拉取、Message-ID 去重、邮件归档、回复链归并、规则/附件/AI 解析、SN 校验、追问草稿、人工复核和工单状态机，实现客户邮件报修从收信到可导出的闭环沉淀与可追溯管理。

### 1.2 一期核心目标

- 自动接收报修邮箱邮件，完成 Message-ID 去重、邮件元数据入库、原始 EML 和附件 OSS 归档。
- 识别新报修、客户补充、内部转发、无关邮件和未知邮件。
- 从正文、标准模板、附件和 AI 候选中抽取结构化报修信息。
- 通过 SN/资产库和板卡/物料规则校验 SN、客户、物料和寄送规则。
- 缺少关键信息时生成追问草稿，默认进入人工审核。
- 低置信度、SN 异常、字段冲突、追问超限、线程不确定、系统异常必须进入人工复核。
- 所有工单状态、字段变更、AI 调用、后台任务和人工动作可追溯。
- 前端提供邮件中心、工单中心、人工复核、自动回复审核、基础资料、AI 日志、系统配置和看板。

### 1.3 一期不做

- 不做正式生产高可用、多租户、复杂权限矩阵和外部系统深度集成。
- 不直接接入 SAP/ITSM，下游导出先以 `ready_for_export` 状态作为边界。
- 不引入 Redis、Celery、Prometheus、Node Exporter。
- 不默认真实自动发送邮件，`AUTO_SEND_ENABLED=false` 是一期安全默认值。
- 不把原始 EML、附件二进制、完整 AI prompt 或真实密钥写入数据库或 Git。
- 工单/邮件行级数据权限未建模，当前仅实现接口级 RBAC。

## §5 核心业务流程

### 5.1 邮件接收 → 工单闭环总流程

```text
1. APScheduler 每 5 分钟触发 imap_poll Job
2. 连接 IMAP，按 UID 拉取未读邮件
3. 通过 message_id 直接查重（uk_emails_message_id）
4. 非重复邮件获取完整 EML 和附件
5. 原始 EML 上传 OSS（upload_bytes_to_oss），附件上传 OSS
6. 写 oss_objects、emails、email_attachments、mail_fetch_records
7. 邮件线程归并（In-Reply-To > 归一化主题 > 新建线程）
8. 规则预解析 + DeepSeek AI 判断邮件类型和字段
9. 如有图片/PDF 附件，调用 Qwen vl_chat 多模态解析
10. 高置信无冲突时自动应用到工单；否则进入人工复核
11. 缺失字段时生成追问草稿（需人工审核）
12. SN 校验（sn_assets + board_cards）
13. 状态流转、审计日志写入
```

### 5.2 邮件摄取处理分层

- **L0 基础预处理**：不调用 AI，只解析 Message-ID、In-Reply-To、References、From/To/Cc、主题、正文摘要、附件元数据
- **L1 轻量分类**：判断 `new_repair`、`customer_reply`、`internal_forward`、`irrelevant`、`unknown`，输出置信度、原因
- **L2 专业字段解析**：模板解析、正文解析、附件解析、AI 字段抽取、缺失字段判断、冲突判断、SN 校验、工单创建或更新

### 5.3 无关邮件策略

```text
INGEST_UNRELATED_POLICY=ignore / metadata_only / archive
```

一期推荐 `metadata_only`，只保存最小元数据，不把无关邮件正文和附件默认放入业务 OSS。

### 5.4 邮件线程与工单关系

必须区分以下对象：

```text
email_threads     = 邮件会话容器
emails            = 每一封真实邮件
repair_tickets    = 报修业务工单
email_ticket_links = 邮件与工单的关联关系
```

严禁把邮件线程直接等同于工单。可能的关联关系：
- 一个 thread 对一个 ticket
- 一封邮件多个 SN，可建一个 ticket 多个 ticket_items，也可人工拆分
- 一个 thread 混入多个报修时，需要人工拆分
- 客户换主题补充旧工单时，多个 threads 可关联同一个 ticket

线程归并优先级：
1. `In-Reply-To` 或 `References` 精确命中已入库邮件
2. 归一化主题相同、发件人域名相同、时间窗口合理
3. 正文或附件中 SN 与已有工单高度一致
4. AI 判断上下文一致
5. 低置信度创建 `thread_uncertain` 人工任务

自动归并必须记录 `merge_confidence`、`merge_reason`、`merge_strategy`。

### 5.5 解析与字段合并优先级

```text
人工锁定字段
> 人工确认字段
> 最新客户回复中的高置信度字段
> 附件结构化字段
> 历史邮件字段
> AI 推测字段
```

重新解析必须遵守：
- 不得覆盖人工锁定字段
- 每次重解析生成新的 `parse_results`，不能覆盖旧结果
- 旧解析结果保留，通过 `apply_status` 标识状态

### 5.6 追问与回复审核

`AUTO_SEND_ENABLED=false` 时：
- 允许生成草稿和审核记录
- 审核通过不等于真实 SMTP 发送
- 接口应返回发送开关状态

追问超过 `MAX_FOLLOW_UP=3` 后，转人工复核。追问次数按工单维度计数。

### 5.7 人工复核必须创建任务的场景

| 场景 | 任务类型 | 说明 |
| --- | --- | --- |
| 解析低置信度 | `low_confidence` | 无法可靠抽取字段 |
| SN 异常 | `sn_error` | SN 不存在、无效、客户/物料不匹配 |
| 字段冲突 | `field_conflict` | 新字段与已有字段冲突 |
| 追问超限 | `followup_limit` | 超过 MAX_FOLLOW_UP |
| 回复待审核 | `reply_review` | 追问草稿需要人工审核 |
| 线程不确定 | `thread_uncertain` | 无法确定邮件归属 |
| 系统异常 | `system_error` | AI、OSS、IMAP、SMTP 等异常 |
| 人工主动创建 | `manual_created` | 用户主动发起复核 |

## §6 数据库使用原则

### 6.1 约束规则

- 状态字段统一使用 `VARCHAR`，不使用数据库 `ENUM`
- 邮件去重主依据：`uk_emails_message_id`（Message-ID 唯一约束）
- 状态流转必须写 `ticket_status_logs`；字段修改必须写 `field_audit_logs` 和 `operation_logs`
- `workflow_*` 只管理工单状态机，不承载邮件、附件、回复、任务、通知等所有状态
- 邮件事实、解析候选、工单当前视图必须分离
- `version` 字段用于乐观锁，防止多人并发覆盖

### 6.2 状态机约束

标准工单状态：

| 状态 | 中文名 | 说明 |
| --- | --- | --- |
| `new_email` | 邮件已入库 | 邮件和附件已归档，尚未解析 |
| `parsed` | 已解析 | 已产生结构化候选，仍需完整性和 SN 校验 |
| `need_customer_info` | 待客户补充 | 缺少关键字段，需要客户补充 |
| `auto_replied` | 已追问 | 已生成追问草稿或已发送追问 |
| `manual_review` | 人工复核 | 低置信度、异常、冲突或超限 |
| `ready_for_export` | 可导出 | 字段完整，SN 校验通过 |
| `error` | 异常 | 系统处理异常 |
| `closed` | 已关闭 | 工单完成或终止 |

标准流转必须通过 `workflow_transitions` 和 `/api/v1/tickets/{id}/transition`：

| 来源 | 目标 | 事件 | 条件 |
| --- | --- | --- | --- |
| `new_email` | `parsed` | `parse_completed` | 至少产生一个解析结果 |
| `new_email` | `manual_review` | `parse_low_confidence` | 初始解析低置信度 |
| `parsed` | `ready_for_export` | `validation_passed` | 字段完整且 SN 校验通过 |
| `parsed` | `need_customer_info` | `missing_fields_detected` | 关键字段缺失且可追问 |
| `parsed` | `manual_review` | `field_conflict` | 字段冲突、SN 异常或置信度不足 |
| `need_customer_info` | `auto_replied` | `reply_draft_created` | 已生成追问草稿 |
| `auto_replied` | `parsed` | `customer_reply_received` | 客户回复归并原线程 |
| 任意非终态 | `manual_review` | `manual_review_required` | 需要人工介入 |
| `manual_review` | `ready_for_export` | `manual_resolved` | 人工修正且校验通过 |
| `manual_review` | `parsed` | `manual_resolved` | 人工修正后回到解析态 |
| 任意非终态 | `error` | `system_error` | 系统异常 |
| 任意非终态 | `closed` | `manual_close` | 人工关闭 |

禁止绕过状态机直接更新 `repair_tickets.current_status_code`。

## §7 权限与安全原则

### 7.1 角色权限

| 角色 | role_code | 权限范围 |
| --- | --- | --- |
| 系统管理员 | `admin` | 用户管理、角色分配、系统配置、基础资料导入、全部业务兜底操作 |
| 主管 | `supervisor` | 查看业务数据、人工任务分配/转派/释放、回复审核、AI 日志、系统配置、工单状态流转 |
| 一般操作员 | `operator` | 查看统一人工任务池，主动领取未分配任务，处理本人已领取/被分配任务，修正字段、SN 校验、采纳解析、生成追问、提交回复草稿 |

### 7.2 接口级 RBAC 方向

- `users`：仅 `admin`
- `manual-review`：列表/详情/领取/释放/处理/重解析允许 `operator/supervisor/admin`；分配/转派仅 `supervisor/admin`
- `replies`：草稿和编辑允许 `operator/supervisor/admin`；审核通过/拒绝仅 `supervisor/admin`
- `master-data`：查询允许 `supervisor/admin`；导入仅 `admin`
- `ai-logs`、`system`、`statistics`：允许 `supervisor/admin`
- 工单状态流转仅 `supervisor/admin`

### 7.3 数据库安全约束

- 真实密码、邮箱凭据、OSS key、AI key、JWT secret 不得进入 Git
- `.env`、`.env.*`、`logs/` 必须被 Git 忽略；仅保留 `.env.example`
- MySQL 不开放公网端口，只允许 Docker 内网、服务器本机和 SSH 隧道访问
- AI 完整 JSONL 日志不得暴露给前端

### 7.4 AI 安全约束

- `AI_API_KEY` / `QWEN_API_KEY` 只从运行环境读取
- 不把 API key 写入源码、文档、测试快照、构建产物或 Git 可追踪文件
- AI 调用日志不记录 key
- 完整 prompt/input/output 写入私有 JSONL；数据库只保存摘要、模型、耗时、状态
- AI 失败不阻断邮件入库或重解析；保留规则候选并转入人工复核
- AI 不得静默覆盖 `manual_locked=1` 字段

### 7.5 开发阶段安全原则

开发阶段必须遵循的安全准则（适用于当前一期内部试运行阶段）：

1. **敏感信息零泄漏**：无论任何环境（本地/测试/联调），API 密钥、JWT Secret、数据库密码、邮箱凭据、OSS 凭据均不得硬编码在源码中。一律通过 `.env` 文件或系统环境变量读取，且 `.env` 文件必须在 `.gitignore` 中明确排除。

2. **默认拒绝原则**：自动发送（SMTP）、自动应用 AI 结果等高风险操作默认关闭。开发期间 `AUTO_SEND_ENABLED=false` 是强约束。

3. **最小权限原则**：数据库连接使用专用账号，不同环境使用不同数据库实例。开发期间不混用生产和测试数据库。代码中使用的数据库账号不应具备 DROP DATABASE 等破坏性权限。

4. **日志脱敏**：日志输出中不得包含密码、API key、JWT 等敏感信息。AI 调用的完整 prompt 和 response 应写入带权限控制的 JSONL 文件而非标准日志流。

5. **前端安全边界**：前端不可获取 AI API key、数据库密码等后端密钥。前端角色隐藏仅作为 UX 优化，真正的权限校验必须在后端 API 层完成。

6. **依赖安全**：依赖包应使用固定版本号（`requirements.txt` / `package.json` 中明确版本），定期检查已知漏洞。不使用已废弃或停止维护的依赖。

7. **错误信息最小化**：生产环境的 HTTP 500 错误不应暴露堆栈信息或内部实现细节。当前开发阶段可保留详细错误用于调试，但需在代码中预留开关。

8. **文件上传安全**：邮件附件和导入文件必须校验类型、大小限制。不信任用户提供的文件名（防止路径遍历）。OSS 上传使用服务端签名（presigned URL），不暴露 AK/SK 到前端。

9. **SQL 注入防护**：100% 使用参数化查询（SQLAlchemy ORM 的 `where()` 条件自动参数化）。严禁字符串拼接 SQL。如确需使用原始 SQL（如 VIEW 创建），必须通过 Alembic 迁移执行并经过代码审查。

10. **XSS 防护**：前端渲染用户输入的邮件正文/主题时，必须进行 HTML 转义。邮件正文中可能包含恶意脚本，前端展示时必须使用 React 的安全渲染（默认转义）或显式消毒处理。

## §8 AI 模块调用原则

### 8.1 双 Provider 架构

系统支持 DeepSeek + Qwen 两种 AI Provider，均为后端执行，前端不直连 AI 服务。

| Provider | 类 | 接口 | 用途 |
| --- | --- | --- | --- |
| DeepSeek | `DeepSeekProvider` | `chat_json` | 邮件分类、字段抽取、追问草稿、回复审查 |
| Qwen | `QwenProvider` | `chat_json` + `vl_chat` | 文本解析 + 多模态附件（图片/PDF）解析 |

切换方式：设置环境变量 `AI_PROVIDER=deepseek` 或 `AI_PROVIDER=qwen`。

### 8.2 调用规则

- 规则解析优先，AI 兜底
- AI 输出必须是结构化 JSON，并通过 Pydantic schema 校验
- 重试机制：可重试错误（超时、5xx、JSON 解析失败）最多重试 `AI_MAX_RETRIES=2` 次
- AI 失败时保留规则候选并转人工复核，不自动创建工单
- 完整请求/响应写入 JSONL（`logs/ai/{yyyy}/{mm}/{dd}/ai-{yyyyMMdd}.jsonl`）
- 数据库 `ai_call_logs` 只保存摘要、模型、耗时、状态和 JSONL 定位

### 8.3 调用链路

```text
邮件入库
-> 规则预解析（classify_email + extract_fields）
-> DeepSeek chat_json 判断邮件类型与字段
-> Qwen vl_chat 解析图片/PDF 附件（如有）
-> 综合 AI 结果，判断置信度
-> 高置信 -> 自动应用到工单
-> 低置信 -> 创建人工复核任务
```

### 8.4 置信度阈值

- `CONFIDENCE_THRESHOLD=0.7`：解析结果置信度低于此值进入人工复核
- `AUTO_SEND_MIN_CONFIDENCE=0.85`：自动发送需 AI 置信度达到此值
- AI 回复草稿 `confidence_score < 0.5` 时丢弃，回退模板

### 8.5 环境变量

```text
AI_PROVIDER=deepseek
AI_API_KEY=         # DeepSeek API key
AI_MODEL=deepseek-v4-flash
AI_BASE_URL=https://api.deepseek.com
AI_TIMEOUT_SECONDS=30.0
AI_MAX_RETRIES=2
AI_MAX_INPUT_CHARS=12000

QWEN_API_KEY=       # 通义千问 API key
QWEN_MODEL=qwen-plus
QWEN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
```

## §12 测试与部署

### 12.1 本地开发前置条件

- Python 3.11+

ssh -N -L 13307:127.0.0.1:3307 <server-alias>

```bash
cd backend
python -m venv .venv

pytest                          # 运行测试（当前 45 passed）
uvicorn app.main:app --reload   # 启动开发服务器
```

数据库迁移：

```bash
cd backend
alembic upgrade head
python -m app.seed
python -m app.db_smoke
```

模型变更流程：

```bash
alembic revision --autogenerate -m "describe schema change"
alembic upgrade head
python -m app.seed
python -m app.db_smoke
pytest
```

### 12.3 前端开发命令

```bash
cd frontend
npm install
npm run typecheck       # 类型检查
npm run build           # 生产构建
npm run dev             # 开发服务器
```

### 12.4 Docker 部署

```bash
cd repair-mail-agent
cp .env.example .env
# 替换 MYSQL_ROOT_PASSWORD、DATABASE_URL、JWT_SECRET 等占位值
docker compose up -d mysql
docker compose up -d --build
docker compose logs -f backend-api
docker compose logs -f nginx
```

容器接入顺序：
1. `mysql`
2. 后端迁移/初始化任务
3. `backend-api`
4. `frontend`
5. `nginx`
6. GitHub Actions 自动部署

### 12.5 部署脚本要求

`deploy.sh` 必须至少包含：
1. 确认项目目录和 `.env` 存在
2. `git pull --ff-only origin main`
3. 部署前备份 MySQL
4. `docker compose up -d mysql` 并等待健康
5. 执行 Alembic 迁移，失败必须退出
6. 执行 seed
7. `docker compose up -d --build`
8. 检查 `/health` 返回成功
9. 输出 `docker compose ps` 和日志定位

迁移失败、构建失败、健康检查失败时必须 `exit 1`。

### 12.6 测试验收标准

阶段性最低验收：
- 后端：`python -m compileall app`、`pytest`、`alembic upgrade head`、`python -m app.seed`、`python -m app.db_smoke`
- 前端：`npm run typecheck`、`npm run build`
- Docker：`docker compose up -d --build`、`/health` 可访问
- 数据库：27 张业务/审计表 + `alembic_version` + `business_emails` VIEW；基础种子数据存在
- Git：本地分支跟踪 `origin/main`，工作区提交前不包含 `.env`、日志、真实密钥
