## 2. 项目目标与一期边界

项目目标：

构建一个邮件报修自动化系统，将系统邮箱中的报修邮件转化为可追踪、可人工兜底、可审核回复、可导出的维修工单。系统以确定性服务层和数据库状态机保证业务正确性，以 AI 辅助完成邮件意图识别、字段抽取、缺失信息判断、回复草稿生成。

一期核心能力：

- 控制台登录、用户管理、角色权限。
- 邮件手工入库、EML 导入、IMAP 定时只读拉取、列表、详情、重新解析和导出。
- 邮件线程归并和人工合并/拆分。
- 入库前 UID/Message-ID/raw EML hash 去重、装饰性内嵌图片过滤和完整规则候选解析。
- 原始 EML 与附件 OSS 归档、临时下载 URL 和附件解析结果展示。
- 规则预解析 + Qwen 附件级解析 + DeepSeek 邮件级结构化解析。
- 解析结果采纳、拒绝、部分采纳。
- 工单字段编辑、明细维护、SN 校验、状态流转、导出。
- 人工复核任务池、系统负责人、处理、重新解析；正常工作流不再领取、分配或释放。
- 回复草稿、话术模板、人工审核、SMTP 发送。
- 基础资料导入导出，包括 SN 资产和板卡寄北京规则。
- 站内通知、AI 日志、操作日志、统计分析、系统配置。

当前不应被误认为已完成的能力：

- OSS 强一致归档已统一：手工、EML、IMAP 均在完整归档 raw EML 和全部附件后才创建正式邮件，失败对象保留元数据供幂等重试。
- 真实 OSS/Qwen 七类附件集成测试和浏览器 E2E 尚未完成。
- IMAP 调度已使用 MySQL 命名锁防止多实例重复执行；每封失败邮件单独记录退避时间，仍需远程镜像和多进程压力验收。
- ORM `relationship()` 尚未系统补齐。
- 行级工单/邮件数据隔离尚未建模。
- LangGraph Agent 工作流尚未接入当前代码。
- 维修收件、寄出等扩展业务事件尚未落地；当前不新建 `ticket_events`，优先复用工单状态、操作日志和系统事件聚合表达。

## 3. 当前实现基线

代码基线：

- 后端：Python 3.11、FastAPI、SQLAlchemy 2.x asyncio、Pydantic Settings、Alembic、MySQL、APScheduler、DeepSeek、Qwen、OSS、IMAP、SMTP。
- 前端：React 18、Vite、TypeScript、Ant Design、React Router、TanStack Query、Axios、Zustand。
- API 前缀：`/api/v1`。
- 当前 ORM 与测试数据库：30 张业务表，另有 Alembic 管理表 `alembic_version`；当前版本 `f7a1b2c3d4e5`。
- 当前代码迁移链已包含 `e6f0a1b2c3d4`（RMA 附件/模板快照）、`f7a1b2c3d4e5`（SN 安全闸门、下游状态、逐用户通知）和 `a8b2c3d4e5f6`（IMAP UIDVALIDITY 幂等分区）；实际数据库升级必须单独授权。
- 当前角色：`admin`、`supervisor`、`operator`。
- 当前工单主状态：`new_email`、`parsed`、`need_customer_info`、`auto_replied`、`manual_review`、`ready_for_export`、`error`、`closed`。
- 当前 `ready_for_export` 口径：字段完整且 SN 校验通过后可进入可导出；客户确认收到维修后设备属于后续事件模型扩展，不是当前进入该状态的硬门槛。

当前正式邮件数据模型：

- 邮件归档使用 `emails`。
- 回复链使用 `email_threads`。
- 邮件与工单关系使用 `email_ticket_links`。
- IMAP UID 幂等和拉取审计使用 `mail_fetch_records`。
- `business_emails` 是基于 `emails` 的数据库视图，不是独立业务实体表。

当前后期目标：

- 维修设备收到、寄出、客户确认收到等业务事件尚未落地，先基于现有日志和状态表设计录入与聚合，不把历史候选表名视为建表目标。
- LangGraph 是后期 Agent 工作流编排层，负责节点编排、条件路由、人工暂停/恢复、执行追踪，不直接替代 service 层。

## 5. 核心业务流程

当前代码事实流程：

1. 邮件从手工 JSON、EML 文件或 IMAP 定时任务进入；IMAP 使用指定账号、`UNSEEN + BODY.PEEK[]` 只读拉取。
2. IMAP 先按 `mailbox_account + folder_name + imap_uid` 去重；所有入口再按规范化 Message-ID 去重。缺失 Message-ID 时以 raw EML SHA-256 生成稳定替代值。
3. `mail_precheck` 在 OSS 前执行完整规则候选解析，产出意图、字段、明细、缺失项、冲突项、置信度和证据；高置信无关且无回复信号、业务明细和有效附件的邮件只记录最小审计。
4. 通过预检后上传 raw EML 和全部附件到 OSS；任一对象失败返回 `OSS_NOT_CONFIGURED/OSS_ARCHIVAL_FAILED`，不得正式入库。
5. 全部目标对象上传成功后，按 `In-Reply-To`、归一化主题和发件域匹配线程，在同一正式事务写入 `emails`、`email_attachments` 和预规则 `parse_results`；异步入口同时写初次解析 job。`oss_objects` 可作为归档暂存和重试台账先存在。
6. `attachment_parser` 处理 `docx/xlsx/csv/txt/html/image/pdf`：文本/表格先本地抽取再调用 Qwen，图片和扫描 PDF 使用短期预签名 URL 调用 Qwen VL。
7. `services/parser.py` 生成正文规则候选，DeepSeek 汇总邮件正文、规则上下文及附件解析结果生成邮件级结构化候选；DeepSeek 不读取附件二进制。
8. 高置信且无缺失/冲突的结果可自动采纳；低置信、缺字段、冲突、附件失败或 AI 不可用进入人工复核。
9. 解析采纳后创建或更新工单，执行 SN 校验、状态流转、追问草稿、人工审核和 SMTP 白名单发送。
10. 邮件、工单及主数据支持导入导出；工单满足字段完整且 SN 校验通过后可进入 `ready_for_export`。

后续 LangGraph 目标流程：

- 将规则分类、附件解析、AI 全量解析、业务校验、工单动作计划、人工复核、回复草稿等步骤编排为 Graph 节点。
- Graph 只负责编排和中间路由，不直接修改 `repair_tickets.current_status_code`。
- 所有状态变化必须通过 `services/workflow.py` 的确定性服务执行。
- Graph 执行实例和节点日志优先复用现有任务、系统与 AI 日志；checkpoint 仅在真实 interrupt/resume 证明必要时评估框架存储。

## 6. 模块边界

认证与权限：

- 登录、当前用户、个人信息和密码修改在 `auth` 模块。
- 用户增删改、启停、角色分配、重置密码在 `users` 模块。
- 权限以后端 `require_roles()` 为最终安全边界。

邮件中心：

- `emails` 保存入站和出站邮件。
- `email_threads` 负责回复链归并。
- `email_ticket_links` 负责邮件与工单关联。
- 当前不是 `business_emails` 模型。

解析与 AI：

- 规则解析是候选和兜底，不应绕过 AI 成为最终业务判断的唯一来源。
- AI 解析候选必须持久化到 `parse_results`。
- AI 调用必须写 `ai_call_logs` 摘要索引和管理员受限 JSONL 明细。JSONL 可保存完整文本 Prompt、请求和响应以支持提示词优化，但必须移除 key、认证头、签名 URL 查询串及 data/base64/二进制，并按 30 天保留。

工单：

- `repair_tickets` 是工单主表。
- `repair_ticket_items` 是设备/SN 明细。
- 工单状态变化必须写 `ticket_status_logs`。
- 字段手工修改和解析采纳必须写 `field_audit_logs`。

人工复核：

- `manual_review_tasks` 是人工兜底入口。
- 低置信、冲突、系统异常、回复失败、超过追问上限等都应进入复核。

回复管理：

- `reply_templates` 存话术模板。
- `reply_records` 存草稿、审核、发送状态。
- 发送只保留两个业务开关：普通回复 `AUTO_SEND_ENABLED=false`，RMA `RMA_AUTO_SEND_ENABLED=true`。旧 `REPLY_SEND_MODE` 与 `RMA_AUTHORIZATION_ENABLED` 仅兼容读取，不再作为新配置入口。

基础资料：

- `sn_assets` 用于 SN 资产校验。
- `board_cards` 用于板卡/物料寄北京规则。

日志与通知：

- 用户操作写 `operation_logs`。
- 系统事件写 `system_event_logs`。
- AI 调用摘要写 `ai_call_logs`。
- 后台任务写 `job_run_logs`。
- 站内消息写 `notification_events`。

## 7. 权限与安全原则

角色：

- `admin`：系统管理员，拥有用户管理、角色分配、系统配置、基础资料维护、全部数据查看和兜底操作能力。
- `supervisor`：主管角色保留但当前不参与正常任务分配流程。
- `operator`：一般操作员可查看和处理全部业务工单、人工复核、回复审批发送、AI 日志、统计和 SN 主数据；系统负责人只影响默认队列和通知。

权限规则：

- 后端 RBAC 是最终边界，前端菜单隐藏只改善体验，不能作为安全措施。
- `admin` 在 `require_roles()` 中默认拥有被保护接口访问能力。
- 高危接口必须显式接入 `require_roles()`。
- 当前尚未实现行级工单/邮件隔离，原因是模型缺少明确业务归属字段；不要在现有代码中硬编码临时隔离规则。

安全规则：

- 真实密钥、密码、邮箱凭据、OSS key、AI key 不进入源码、文档、测试快照和构建产物。
- AI API key 只从运行环境读取。
- AI 日志不记录 key。
- 数据库日志不得保存正文、附件全文或完整模型请求响应；完整文本语义仅允许进入管理员受限 AI JSONL，禁止写入密钥、认证头、完整签名 URL、data/base64 或附件二进制。
- 前端 localStorage token 存在 XSS 风险，生产环境可后续评估 httpOnly cookie 或更严格 CSP。

## 7.5 开发阶段安全原则

**⚠️ 最高优先级 — 违反此原则可能导致生产事故。**

开发阶段邮件发送限制：

- 项目处于开发阶段，**无论如何不允许直接给真实客户邮箱发送邮件**。
- 当前测试环境固定 IMAP 收件账号和 SMTP 发件账号均为 `rmatest1@accotest.com`；系统只从该账号的 INBOX 捞取业务邮件，也只以该账号作为 SMTP 登录账号和 From。`rmatest2@accotest.com` 仅作为模拟客户收件邮箱，SMTP 白名单只能包含该地址；文档和仓库禁止记录密码。
- SMTP 收件人白名单由 `SMTP_RECIPIENT_WHITELIST` 控制，代码默认空集合并阻断全部发送；完整 `To + Cc` 集合必须是白名单子集，且在发送准备和网络调用前重复校验。
- 服务启动日志只输出白名单数量，不输出邮箱地址；若白名单为空，所有外发邮件被完全阻断并输出 WARNING 级别告警。
- 任何代码修改涉及 SMTP 发信逻辑时，必须确认白名单机制未被绕过。

## 8. 数据库使用原则

当前数据库以 ORM 和 Alembic 为事实源，当前为 30 张业务表。任何字段、约束、索引、迁移判断必须查 `docs/02-数据库详细设计文档.md` 和当前代码。

原则：

- 新表和字段必须有 Alembic 迁移。
- 修改表结构必须同步 ORM、迁移、测试和数据库文档。
- 状态枚举优先使用 `workflow_statuses` 和 `workflow_transitions` 的种子数据。
- 业务状态流转必须写 `ticket_status_logs`。
- 字段级修改必须写 `field_audit_logs`。
- 解析结果应用状态使用 `parse_results.apply_status`，保留 `accepted` 兼容字段。
- 不要把大文本或附件全文写入 Graph 节点日志；应写业务表、OSS、AI 日志或附件解析结果，并在日志中引用 ID。

## 9. AI 模块调用原则

当前 AI Provider：

- `AI_PROVIDER=deepseek`
- `AI_MODEL=deepseek-v4-flash`
- `AI_PROMPT_VERSION=deepseek-v4-json-v1`
- `MULTIMODAL_PROVIDER=qwen`
- `QWEN_VL_MODEL=qwen-vl-plus`
- Qwen 已作为附件级解析 Provider 接入；DeepSeek 只消费正文、规则候选和附件解析结果。

调用原则：

- 前端不直连模型服务。
- AI 必须输出 JSON，并由 Pydantic 校验。
- AI 不确定的字段必须进入 `missing_fields` 或 `conflict_fields`，不得编造。
- AI 失败不阻断邮件入库，必须转人工复核。
- AI 低置信度、字段冲突、SN 异常、邮件类型不明确必须可追溯。
- Prompt、输入摘要、输出摘要、trace、耗时、状态、关键结构化结果必须可查。
- 真实 Prompt 模板和样例维护在 `docs/04-项目开发资料文档.md`。

## 10. 状态流转原则

当前 8 个主状态：

| 状态 | 当前含义 |
| --- | --- |
| `new_email` | 邮件和附件已归档，尚未完成解析 |
| `parsed` | 邮件内容已完成结构化解析 |
| `need_customer_info` | 缺少 SN、故障描述或联系方式等必要字段 |
| `auto_replied` | 追问邮件已由 SMTP 成功发送，等待客户回复 |
| `manual_review` | 解析置信度不足、冲突或异常，需要人工处理 |
| `ready_for_export` | 工单字段已确认，可以导出或下游同步 |
| `error` | 系统处理失败，等待排查或重试 |
| `closed` | 工单完成或终止 |

当前合法流转由 `workflow_transitions` 控制，必须通过 `transition_ticket()` 执行。不要直接给 `repair_tickets.current_status_code` 赋值，除非是在明确的工单创建初始化场景。

扩展业务事件：

- 导出完成已通过 `ticket_status_logs` 的 `export_completed` 事件表达。
- 维修设备收到、寄出、客户确认等未来事件先做字段和 API 契约设计，优先复用 `ticket_status_logs`、`operation_logs`、`system_event_logs` 与时间线聚合。
- 只有现有表无法满足查询、约束或审计要求并有真实使用证据时，才单独评估迁移；不得预先创建低利用事件表。

## 11. 前后端协作规范

API：

- 统一使用 `/api/v1` 前缀。
- 新接口必须在 `backend/app/api/v1/router.py` 注册。
- 业务逻辑放 service，不放路由函数里。
- 错误使用明确错误码，例如 `TICKET_NOT_FOUND`、`WORKFLOW_TRANSITION_NOT_ALLOWED`。
- 高危接口必须接 RBAC。

前端：

- 所有接口封装在 `frontend/src/api/client.ts`。
- 所有共享类型维护在 `frontend/src/types/api.ts`。
- 页面路由维护在 `frontend/src/routes/router.tsx`。
- 菜单权限和按钮隐藏不能替代后端权限。
- 接口字段变更必须同步类型、页面展示、错误文案和测试。

## 当前开发硬规则

- 邮件原件和附件上传 OSS 前，必须先完成 IMAP UID 去重、Message-ID 去重和高置信无关邮件预筛选；无关邮件只记录最小审计信息，不创建正式业务邮件。
- DeepSeek 是正文、规则上下文、附件解析结果汇总后的邮件级结构化文本 Provider；Qwen 是附件级 Provider，文本类附件使用本地抽取结果，图片和扫描 PDF 使用视觉解析。
- 通过预检查的邮件必须完整归档 raw EML 和全部附件后才能正式入库；三个入口已执行该硬规则，后续修改必须保留失败阻断测试。
- 装饰性内嵌图片在归档前剔除，不创建独立 OSS 对象、附件记录或 Qwen 调用；原始 EML 仍原样归档。HTML 表格属于正文，不拆成独立附件对象。
- 回复草稿创建不改变工单为 `auto_replied`；不可自动发送时进入或保持 `manual_review` 并只创建 `reply_review`，SMTP 成功后才以 `reply_sent` 转为 `auto_replied`。
- `unknown`、低置信、疑似业务邮件不得在预筛阶段丢弃，必须继续进入 OSS/入库/人工审核路径。
- IMAP 默认只读拉取：`UNSEEN + BODY.PEEK[]`，不标记已读，不移动邮件；SMTP 白名单仍是硬安全边界。
- 邮件中心的“立即捞取”仅向 operator/admin 展示，调用 `POST /emails/fetch/jobs`；supervisor 仅保留后端兼容权限，暂停正常业务使用。
- SQL Server 中转适配器为配置驱动占位，默认 `disabled`；配置未完整时不得执行 ODBC 或任何外部网络访问。

## 16. 2026-07-16 业务安全基线

以下规则优先于本文较早章节中的旧描述：

- 固定顺序为 `EML 导入 → 线程聚合 → 解析/人工修正 → SN 核心校验 → 其余安全校验 → ready_for_export → RMA/SQL 下游任务 → closed`。
- `POST /tickets/{id}/validate-sn` 只完成 SN 第一阶段，不得直接进入 `ready_for_export`；只有 `validate-export` 可以执行完整闸门。
- SN 校验必须基于 `sn_assets` 的存在性、有效状态、客户、物料和保修日期证据。SQL Server 关闭时只读本地镜像。
- `ready_for_export` 表示不可变输出快照已通过全部检查；通用状态流转、自动解析和人工任务都不得绕过完整闸门。
- 新 RMA 授权表只有一个双语 AUTO 版本 `rma_authorization_auto_v3_1`。国内外邮件正文模板与 PDF 模板是两套独立版本概念，旧模板标识只用于历史读取。
- RMA 只为客户新报修首次生成。普通回复、补充、内部转发和收货事件不会重复生成。
- SMTP 最底层发送前必须再次验证登录账号等于 From、精确白名单、RMA 单一 To、空 Cc/Bcc；不确定发送结果不得自动重试。
- Miya 负责中文、Demi 负责英文、未知语言由 Miya 兜底；后续邮件继承负责人。负责人不是数据权限边界。

## 17. 2026-07-20 邮件与闭单新基线

- 邮件线程只允许 `References/In-Reply-To → Message-ID` 精确关联；归一化主题仅用于搜索和展示，禁止自动或人工合并工单。
- 客户必填字段由 `intent_type` 决定。新报修必填客户名称、联系人、客户邮箱、报修日期、寄回地址、故障描述和至少一条有效 SN；电话选填，客户编码及物料优先由 SN 主数据补全。
- 发送开关拆分为普通回复、缺失必填字段自动追问、自动附带 RMA PDF。普通回复是主控，RMA 开关不得独立发送邮件。
- 所有 SMTP 路径固定为测试邮箱单一信封；开启任一发送开关必须同步通过 IMAP 只读、SMTP 登录/NOOP 和离线 RMA 预检。
- `device_received` 表示公司收到客户寄来的待修设备。只有 RMA 已发送且公司收货确认回复明确发送成功，工单才能关闭。
- 追问次数只按成功发送的 `missing_fields` 回复计数；草稿、RMA、普通确认和收货确认均不计数。
