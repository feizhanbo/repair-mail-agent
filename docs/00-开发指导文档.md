## 2026-08-12 邮箱级富文本回复基线

- 回复正文只以直接父邮件的原始 `.eml` 为历史引用源，不再逐封拼接数据库线程正文；父邮件正文已包含更早历史时必须原样继承，避免重复引用膨胀。
- 模板库只生成本次新回复。富文本渲染器负责保留父邮件 HTML 结构、表格、安全样式、链接、外链图片、data image 及 HTML 实际引用的 CID MIME 资源，不参与 AI/OCR 或业务语义分析。
- CID 是否继承只依据清理后 HTML 的真实 URL/CSS 引用，不依据 `Content-Disposition`；CID 必须确定性重映射。历史普通附件不得复制，本次 RMA PDF 作为唯一新业务附件添加。
- 父邮件原始 EML、OSS、正文或 CID 证据缺失/冲突时阻止发送并转人工，不允许用数据库简化正文降级发送。发送前复核父 EML 快照，变化后旧草稿必须重新生成。
- 出站归档和 SMTP 必须使用同一份已组装 MIME 对象；`In-Reply-To`、`References` 和既有主题规则保持不变。

## 2026-08-11 RMA 邮件分层分类与闭单基线

本节为现行口径，优先于本文后续历史说明。分类必须同时回答“邮件是什么”和“系统下一步做什么”，邮件分类不得直接等同工单状态。

| 处理层级 | 意图 | 系统动作 |
| --- | --- | --- |
| `auto_repair`（FIRST） | `new_repair`、`thread_new_repair`、`customer_supplement` | 创建或关联标准报修工单，合并字段并进入校验、追问或 RMA 链路 |
| `manual_rma_business`（SECOND） | `component_replacement_repair`、`onsite_service`、`warranty_status_inquiry`、`repair_thread_other` | 明确识别后通知人工；同线程存在 FIRST 时创建独立 `manual_business` 工单，不修改 FIRST |
| `lifecycle_only`（THIRD） | 待修设备入库、维修后发出、客户收货、合同、发票、非我司设备报价 | 可关联生命周期历史，但不建标准报修工单、不生成 RMA、不通知人工 RMA 处理 |
| `unknown` | 无法可靠识别、上下文不足或多意图不能安全拆分 | 建邮件级人工任务，不创建标准报修工单 |

- `EmailThread` 是 RFC 对话链，`RepairTicket` 是业务实例；一个线程允许关联多个工单，关闭工单不拆分邮件线程。
- 保修状态问询属于 SECOND；“设备已过保，请报修”是陈述保修事实并提出维修请求，仍可属于 FIRST。
- THIRD 与 UNKNOWN 严格分开：THIRD 已明确识别且无需进入 RMA 生成，UNKNOWN 是无法可靠判断。
- `manual_business` 只能由人工处理并以 `manual_review → resolved / manual_business_resolved` 结束，禁止进入 SAP、RMA 或 `closed`。
- 标准报修唯一闭单事件是 RMA SMTP 成功、PDF 与出站 EML 归档并通过事实校验后的 `rma_sent → closed / rma_issued_and_archived`。`closed` 不可逆。
- 待修设备到货不再是闭单条件；收货确认字段、服务、界面操作和自动回复模板已从现行功能移除，历史事实迁移到操作日志和生命周期关联。

## 2026-08-11 后端安全删除基线

- 删除能力采用“预览 → 短时确认令牌 → 数据库事务删除 → OSS 可重试补偿”四段式流程，只有 admin 可以调用。Controller 只做鉴权、参数和响应，依赖分析与事务集中在删除 Service。
- ORM 已为邮件、线程、附件、工单、解析、人工任务、回复、RMA、SAP、通知、日志和 OSS 补齐双向 `relationship()`；所有关系使用明确 `foreign_keys/back_populates`，禁止 ORM `delete/delete-orphan` 级联，避免删除工单时误删邮件。
- 删除审计复用 `operation_logs`，OSS 外部动作复用 `external_operation_records`，补偿任务复用 `job_run_logs`；当前三表能够覆盖操作者、目标、前后快照、外部动作状态、错误和重试，不新增第二套删除审计模型。
- 删除工单只删除工单聚合数据并解除邮件/线程关联，邮件历史默认保留。来源邮件、生命周期证据、已应用解析、已发送回复、运行中任务和已执行外部业务均受保护。
- OSS 只能通过持久化的 bucket、object_key、endpoint、object_version 定位，禁止从 URL 猜 Key。数据库先提交删除事实，OSS 失败进入持久化重试；对象不存在视为幂等成功，共享对象仍有引用时不得删除。

## 2026-08-05 入站邮件、原线程回复与附件基线

- 当前代码 Alembic 单一 head 为 `m0h5c6d7e8f9`，受控测试库 `repair_system_test` 已经由仅绑定 `127.0.0.1:13307` 的隧道升级到该版本。系统只处理目标邮箱作为收件人的入站邮件：目标地址可出现在 `To`、`Cc`、`Delivered-To` 或 `X-Original-To`；`From` 为目标邮箱自身时必须终止为 `SELF_SENT_MAIL_SKIPPED`。

- 国内 RMA 根据 SN 保修起止日期与工单报修日期选择 `domestic_in_warranty_v1` 或 `domestic_out_warranty_v1`；缺失、非法或同工单混合保修状态转人工。模板选择不由最终收费状态代替。
- 客户补充邮件必须是真实回复：RFC 头指向系统追问，正文包含新补充段和被回复邮件原文引用；解析只使用 `latest_reply_segment`，不得把引用内容当作客户新输入。
- RMA PDF 只嵌入当前文档实际使用字符的字体子集；字体子集失败即停止生成，附件超过 2,000,000 字节即停止发送。模板未提供的数据字段保持空白，不猜测填充。
- 真实邮件测试必须保留“AI 原结果 → 人工修正 → 安全重验 → 外部提交 → SMTP/OSS 证据”的完整链路。测试脚本或人工工具不得用未经编码校验的命令行中文常量覆盖 AI/主数据字段；PDF 发送前必须以最终不可变快照逐页视觉验收。

## 2026-07-30 RMA 签发闭环（最高优先级现行口径）

- `rma_sent` 表示 SMTP 服务端已明确接受 RMA 回复，且系统已保存发送 Message-ID；它是短暂的归档恢复状态。
- 只有正式 RMA 编号、RMA PDF、PDF 关键字段校验、SMTP 成功、Message-ID、PDF 归档和出站 EML 归档全部可验证时，才以 `rma_issued_and_archived` 进入 `closed`。
- `closed` 表示当前报修的 RMA 已签发完毕，不再等待公司收货，也不再自动推进。设备收货只能记录审计事实，不发确认邮件、不改变工单状态。
- SMTP 已成功但归档失败时只重试归档，严禁重复发送；归档重试三次后保留失败原因、恢复节点并转人工。
- 已闭合线程收到后续邮件时先建立新邮件处理节点并重新分类；不得因旧工单已关闭而直接判人工。若是新的 `new_repair`，在带前序关系的新线程创建新工单。
- RMA 邮件以最新一封有效客户入站邮件为直接父邮件，`In-Reply-To` 指向该父邮件，`References` 保存从最初报修到直接父邮件的完整链。业务主题为 `RMA{RMA编号}{客户名称}`；测试信封发送时另由安全层增加 `[TEST ONLY]`。
- 国内维修寄回路线按板卡字段匹配，不能使用 SAP 物料字段推断；海外范围按客户政策或人工确认后统一使用北京默认路线。
- 特殊价格、非 RMB/USD 币种、匿名、特殊称呼等定制需求当前不进入自动签发。人工任务必须给出恢复节点和处理方式，且仍须遵守模板、原线程、发送记录和归档记录要求。
- SQL Server 表写入以本地预生成并持久化的 `SourceRequestID` 为唯一远端身份；一张工单的全部 SN 必须在同一 SQL Server 事务中提交，技术重试复用原 ID，业务版本变化生成新 ID。

## 2026-07-28 RMA/SAP 闭环基线（当前事实）

系统开发必须同时满足以下五项基础原则：

1. 任何邮件都有明确分类结果。
2. 任何业务工单都有明确当前状态。
3. 任何异常都有可恢复节点。
4. 任何终止都有终止原因。
5. 任何外部操作都可以判断是否已经执行。

状态边界不得混用：

- 邮件状态描述“一封邮件处理到了哪里”，由 `parse_status`、`intent_type`、`processing_stage`、`terminal_reason_code`、`last_error_code`、`retryable` 和 `next_retry_at` 表达。
- 工单主状态描述“报修业务走到了哪里”，主链为 `new_email → parsed/need_customer_info/manual_review → ready_for_export → rma_sent → closed`。
- `ready_for_export` 只表示已经通过 SN、字段和安全快照校验，具备向 SAP 导出条件。
- SAP 整批写入、SourceRequestID 回查、RMA 回填和失败重试属于外部操作子状态，不写入邮件处理状态。
- 只有 RMA 模板邮件实际 SMTP 发送成功且保存 Message-ID，工单才进入 `rma_sent`；只有 PDF 与出站邮件归档核验完成才进入 `closed`。

RMA/SAP 责任边界：

- 本系统不生成 RMA 编号，只接收并校验 SQL Server `U_CustomerNum` 回填的 `yyyyMMddNN`。
- 一张工单形成一个不可变 `ticket_relay_exports` 批次；每个 `repair_ticket_items` 明细形成一条 `export_sap`，即一行一 SN。
- 同工单全部 SN 回填同一 RMA 时生成一份 PDF 并按模板在原邮件链回复；回填多个 RMA、非法 RMA、政策冲突或地址冲突时进入人工复核。
- 所有外发必须命中模板库，并保留原邮件主题、`In-Reply-To` 和 `References`；系统不创建脱离原线程的全新客户邮件。
- 当前 ORM 为 35 张业务表，代码 Alembic 单一 head 与目标测试库 revision 均为 `k8f3a4b5c6d7`；生产库仍须单独授权、备份和核验。

## 2. 项目目标与一期边界

项目目标：

构建一个邮件报修自动化系统，将系统邮箱中的报修邮件转化为可追踪、可人工兜底、可审核回复、可导出的维修工单。系统以确定性服务层和数据库状态机保证业务正确性，以 AI 辅助完成邮件意图识别、字段抽取和缺失信息判断；正式回复正文由模板库确定性生成。

一期核心能力：

- 控制台登录、用户管理、角色权限。
- IMAP 定时/立即只读拉取、邮件列表、详情和重新解析。手工 JSON/EML 导入及邮件导出仅保留后端兼容 API，不在邮件中心提供入口。
- 邮件线程归并和人工合并/拆分。
- 入库前 UID/Message-ID/raw EML hash 去重、装饰性内嵌图片过滤和完整规则候选解析。
- 原始 EML 与附件 OSS 归档、临时下载 URL 和附件解析结果展示。
- 规则预解析 + Qwen 附件级解析 + DeepSeek 邮件级结构化解析。
- 解析结果采纳、拒绝、部分采纳。
- 工单字段编辑、明细维护、SN 校验、状态流转、导出。
- 人工复核任务池、系统负责人、处理、重新解析；正常工作流不再领取、分配或释放。
- 回复草稿、话术模板、人工审核、SMTP 发送。
- 基础资料导入导出，包括 SN 资产和板卡寄北京规则。
- 站内通知、AI 日志、操作日志、统计分析、系统配置。

当前不应被误认为已完成的能力：

- OSS 强一致归档已统一：手工、EML、IMAP 均在完整归档 raw EML 和全部附件后才创建正式邮件，失败对象保留元数据供幂等重试。
- 真实 OSS/Qwen 七类附件集成测试和浏览器 E2E 尚未完成。
- IMAP 调度已使用 MySQL 命名锁防止多实例重复执行；每封失败邮件单独记录退避时间，仍需远程镜像和多进程压力验收。
- SMTP、RMA 和公司收货确认虽然已有发送代码，但当前最底层信封仍固定为测试账号，不能作为生产客户发信能力。
- `AUTO_FOLLOWUP_ENABLED`、间隔配置和 `auto_followup` job handler 已存在，但没有周期扫描或生产入队路径；当前只有首轮事件驱动追问和人工触发追问。
- SQL Server 访问统一经过 `integrations/sap_middleware`；已实现 SN 全量快照、一行一 SN 整批事务写入和按 SourceRequestID 批量轮询。CallID 仅作为历史只读审计字段。
- 人工复核不得直接关闭工单；只有 RMA 签发与归档六项闸门通过，且状态机从 `reply_records`、`ticket_rmas`、出站 `emails`、PDF OSS 对象及附件关联重新核对持久化事实后才允许闭单。业务取消须后续设计独立终止状态和原因。
- 当前后端全量 pytest 已恢复：2026-07-30 结果为 `299 passed, 1 skipped, 2 warnings`，PowerShell 实测墙钟约 35 秒；默认跳过的真实数据库冒烟项已通过独立回环 SSH 隧道实测。
- ORM `relationship()` 尚未系统补齐。
- 行级工单/邮件数据隔离尚未建模。
- LangGraph Agent 工作流尚未接入当前代码。
- 维修收件、寄出等扩展业务事件尚未落地；当前不新建 `ticket_events`，优先复用工单状态、操作日志和系统事件聚合表达。

## 5. 核心业务流程

当前代码事实流程：

1. 邮件从手工 JSON、EML 文件或 IMAP 定时任务进入；IMAP 使用指定账号、`UNSEEN + BODY.PEEK[]` 只读拉取。
2. IMAP 先按 `mailbox_account + folder_name + imap_uid` 去重；所有入口再按规范化 Message-ID 去重。缺失 Message-ID 时以 raw EML SHA-256 生成稳定替代值。
3. `mail_precheck` 在 OSS 前执行完整规则候选解析，产出意图、字段、明细、缺失项、冲突项、置信度和证据；高置信无关且无回复信号、业务明细和有效附件的邮件只记录最小审计。
4. 通过预检后上传 raw EML 和全部附件到 OSS；任一对象失败返回 `OSS_NOT_CONFIGURED/OSS_ARCHIVAL_FAILED`，不得正式入库。
5. 全部目标对象上传成功后，只按 `References/In-Reply-To → Message-ID` 精确关系匹配活动线程；归一化主题和发件域只用于搜索、展示和审计，不参与自动归并。若精确父邮件属于已关闭工单，系统创建新线程。在同一正式事务写入 `emails`、`email_attachments` 和预规则 `parse_results`；异步入口同时写初次解析 job。`oss_objects` 可作为归档暂存和重试台账先存在。
6. 归档前以扩展名、声明 MIME 和文件魔数识别 ZIP、RAR、7Z、TAR、TAR.GZ/TGZ/GZIP；压缩容器统一作为 `engineering_reference` 原样私有归档，写 `parse_status=skipped`，不解压、不调用 Qwen、不参与 RMA 字段提取，也不因其未扫描或无法读取内容转人工。DOCX/XLSX 虽为 ZIP 容器，但仍按现有业务附件处理。
7. `attachment_parser` 处理 `docx/xlsx/csv/txt/html/image/pdf`：文本/表格先本地抽取再调用 Qwen，图片和扫描 PDF 使用短期预签名 URL 调用 Qwen VL；工程辅助压缩附件的 `skipped` 是终态，重新解析不得重复下载或调用模型。
8. `services/parser.py` 生成正文规则候选，DeepSeek 汇总邮件正文、规则上下文及普通业务附件解析结果生成邮件级结构化候选；压缩附件只提供文件名、格式和“工程辅助资料已保存”元数据，不提供二进制或工程结论。
9. 高置信且无缺失/冲突的结果可自动采纳；低置信、缺字段、冲突、业务附件失败或 AI 不可用进入人工复核。工程辅助压缩附件不属于阻断性附件失败。
10. 解析采纳后创建或更新工单，执行 SN 校验、状态流转、追问草稿、人工审核和 SMTP 白名单发送。
11. 工单及主数据支持导入导出；邮件手工导入/导出仅保留 deprecated 后端兼容接口。工单满足字段完整且 SN 校验通过后可进入 `ready_for_export`。

后续 LangGraph 目标流程：

- 将规则分类、附件解析、AI 全量解析、业务校验、工单动作计划、人工复核、回复草稿等步骤编排为 Graph 节点。
- Graph 只负责编排和中间路由，不直接修改 `repair_tickets.current_status_code`。
- 所有状态变化必须通过 `services/workflow.py` 的确定性服务执行。
- Graph 执行实例和节点日志优先复用现有任务、系统与 AI 日志；checkpoint 仅在真实 interrupt/resume 证明必要时评估框架存储。

## 6. 模块边界

认证与权限：

- 登录、当前用户、个人信息和密码修改在 `auth` 模块。
- 用户增删改、启停、角色分配、重置密码在 `users` 模块。
- 权限以后端 `require_roles()` 为最终安全边界。

邮件中心：

- `emails` 保存入站和出站邮件。
- `email_threads` 负责回复链归并。
- `email_ticket_links` 负责邮件与工单关联。
- 当前不是 `business_emails` 模型。

解析与 AI：

- 规则解析是候选和兜底，不应绕过 AI 成为最终业务判断的唯一来源。
- AI 解析候选必须持久化到 `parse_results`。
- AI 调用必须写 `ai_call_logs` 摘要索引和管理员受限 JSONL 明细。JSONL 可保存完整文本 Prompt、请求和响应以支持提示词优化，但必须移除 key、认证头、签名 URL 查询串及 data/base64/二进制，并按 30 天保留。

工单：

- `repair_tickets` 是工单主表。
- `repair_ticket_items` 是设备/SN 明细。
- 工单状态变化必须写 `ticket_status_logs`。
- 字段手工修改和解析采纳必须写 `field_audit_logs`。

人工复核：

- `manual_review_tasks` 是人工兜底入口。
- 低置信、冲突、系统异常、回复失败、超过追问上限等都应进入复核。

回复管理：

- `reply_templates` 存话术模板。
- `reply_records` 存草稿、审核、发送状态，并分别记录具体内容模板 `template_id` 与国内公司基础模板 `base_template_id`。
- 系统不得创建全新业务邮件。每个可发送回复必须关联同工单、同线程的入站父邮件，并包含父邮件 `Message-ID` 对应的 `In-Reply-To` 和 `References`。
- 国内回复由具体内容模板嵌入“所有回复邮件基础模板”；该基础模板只承载公司信息、签名和保密声明，不替代具体业务内容。国外回复按业务类型直接选择指定英文模板。
- 模板缺失、父邮件缺失、跨线程、父邮件无 Message-ID 或发送前审计失败时必须阻断 SMTP 并转人工，不得使用代码 fallback 或 AI 改写后绕过模板。
- 发送只保留两个业务开关：普通回复 `AUTO_SEND_ENABLED=false`，RMA `RMA_AUTO_SEND_ENABLED=true`。旧 `REPLY_SEND_MODE` 与 `RMA_AUTHORIZATION_ENABLED` 仅兼容读取，不再作为新配置入口。

基础资料：

- `sn_assets` 用于 SN 资产校验。
- `board_cards` 用于板卡/物料寄北京规则。

日志与通知：

- 用户操作写 `operation_logs`。
- 系统事件写 `system_event_logs`。
- AI 调用摘要写 `ai_call_logs`。
- 后台任务写 `job_run_logs`。
- 通知事件统一写 `notification_events`，逐用户阅读/解决状态写 `notification_user_states`。
- 通知中心是“当前待关注报修问题”的聚合查询视图；站内消息是全部通知事件历史，二者不得分别写消息表或双写事件。
- 已读不代表业务问题解决；只有人工任务、工单状态、SAP/RMA 外部操作明确完成后，才将用户状态置为 `resolved`。

## 7. 权限与安全原则

角色：

- `admin`：系统管理员，拥有用户管理、角色分配、系统配置、基础资料维护、全部数据查看和兜底操作能力。
- `operator`：一般操作员可查看和处理全部业务工单、人工复核、回复审批发送、AI 日志、统计和 SN 主数据；系统负责人只影响默认队列和通知。

权限规则：

- 后端 RBAC 是最终边界，前端菜单隐藏只改善体验，不能作为安全措施。
- `admin` 在 `require_roles()` 中默认拥有被保护接口访问能力。
- 高危接口必须显式接入 `require_roles()`。
- 当前尚未实现行级工单/邮件隔离，原因是模型缺少明确业务归属字段；不要在现有代码中硬编码临时隔离规则。

安全规则：

- 真实密钥、密码、邮箱凭据、OSS key、AI key 不进入源码、文档、测试快照和构建产物。
- AI API key 只从运行环境读取。
- AI 日志不记录 key。
- 数据库日志不得保存正文、附件全文或完整模型请求响应；完整文本语义仅允许进入管理员受限 AI JSONL，禁止写入密钥、认证头、完整签名 URL、data/base64 或附件二进制。
- 前端 localStorage token 存在 XSS 风险，生产环境可后续评估 httpOnly cookie 或更严格 CSP。

## 7.5 开发阶段安全原则

**⚠️ 最高优先级 — 违反此原则可能导致生产事故。**

开发阶段邮件发送限制：

- 项目处于开发阶段，**无论如何不允许直接给真实客户邮箱发送邮件**。
- 当前测试环境固定 IMAP 收件账号和 SMTP 发件账号均为 `rmatest1@accotest.com`；系统只从该账号的 INBOX 捞取业务邮件，也只以该账号作为 SMTP 登录账号和 From。`rmatest2@accotest.com` 仅作为模拟客户收件邮箱，SMTP 白名单只能包含该地址；文档和仓库禁止记录密码。
- SMTP 收件人白名单由 `SMTP_RECIPIENT_WHITELIST` 控制，代码默认空集合并阻断全部发送；完整 `To + Cc` 集合必须是白名单子集，且在发送准备和网络调用前重复校验。
- 服务启动日志只输出白名单数量，不输出邮箱地址；若白名单为空，所有外发邮件被完全阻断并输出 WARNING 级别告警。
- 任何代码修改涉及 SMTP 发信逻辑时，必须确认白名单机制未被绕过。

## 8. 数据库使用原则

当前数据库以 ORM 和 Alembic 为事实源，当前 ORM 映射 38 张业务表。任何字段、约束、索引、迁移判断必须查 `docs/02-数据库详细设计文档.md` 和当前代码。

原则：

- 新表和字段必须有 Alembic 迁移。
- 修改表结构必须同步 ORM、迁移、测试和数据库文档。
- 状态枚举优先使用 `workflow_statuses` 和 `workflow_transitions` 的种子数据。
- 业务状态流转必须写 `ticket_status_logs`。
- 字段级修改必须写 `field_audit_logs`。
- 解析结果应用状态使用 `parse_results.apply_status`，保留 `accepted` 兼容字段。
- 不要把大文本或附件全文写入 Graph 节点日志；应写业务表、OSS、AI 日志或附件解析结果，并在日志中引用 ID。

## 9. AI 模块调用原则

当前 AI 调用边界：

- 五类业务任务由 `backend/config/llm_routes.yaml` 分别声明主路由、备用路由、模型、超时和重试；当前文本主模型为 `deepseek-chat`，附件视觉主模型为 `qwen-vl-plus`。
- 密钥和 Base URL 只来自环境变量；YAML 和系统配置 API 不公开密钥。
- Prompt 的可执行事实源为 `backend/app/ai/prompts.py`，版本与 SHA-256 写入 `AiCallLog`。
- 仅超时、限流、连接失败和 5xx 可切备用路由；非法 JSON/Schema 不跨模型掩盖。
- 邮件入口分类与 FIRST 字段抽取是两个任务；字段抽取不得改写已锁定意图。

调用原则：

- 前端不直连模型服务。
- AI 必须输出 JSON，并由 Pydantic 校验。
- AI 不确定的字段必须进入 `missing_fields` 或 `conflict_fields`，不得编造。
- 前置分类失败必须降为 UNKNOWN 最小持久化并转高优先级人工复核，绝不进入 FIRST。
- AI 低置信度、字段冲突、SN 异常、邮件类型不明确必须可追溯。
- Prompt、输入摘要、输出摘要、trace、耗时、状态、关键结构化结果必须可查。
- 真实 Prompt 模板和样例维护在 `docs/04-项目开发资料文档.md`。

## 10. 状态流转原则

当前 9 个主状态：

| 状态 | 当前含义 |
| --- | --- |
| `new_email` | 邮件和附件已归档，尚未完成解析 |
| `parsed` | 邮件内容已完成结构化解析 |
| `need_customer_info` | 缺少 SN、故障描述或联系方式等必要字段 |
| `auto_replied` | 追问邮件已由 SMTP 成功发送，等待客户回复 |
| `manual_review` | 解析置信度不足、冲突或异常，需要人工处理 |
| `ready_for_export` | 工单字段已确认，可以导出或下游同步 |
| `rma_sent` | 全部 SN 已取得唯一一致的合法 RMA，模板回复已在原线程发送成功 |
| `error` | 系统处理失败，等待排查或重试 |
| `closed` | 正式 RMA、PDF 校验、SMTP、Message-ID、PDF 与出站 EML 归档全部完成 |

当前合法流转由 `workflow_transitions` 控制，规范上必须通过 `transition_ticket()` 执行。不要直接给 `repair_tickets.current_status_code` 赋值，除非是在明确的工单创建初始化场景。代码审计发现安全快照失效路径仍有直接写 `manual_review` 再补日志/任务的实现，这是待收敛缺口，不是可复制模式。

扩展业务事件：

- SAP 外部阶段由 `ticket_relay_exports` 和 `export_sap` 表达，不创建 `exported` 主状态。
- 公司收货事实只写入工单审计字段，不发送确认邮件、不触发闭单或重新推进。
- 只有现有表无法满足查询、约束或审计要求并有真实使用证据时，才单独评估迁移；不得预先创建低利用事件表。

## 当前开发硬规则

- 邮件原件和附件上传 OSS 前，必须先完成 IMAP UID 去重、Message-ID 去重和高置信无关邮件预筛选；无关邮件只记录最小审计信息，不创建正式业务邮件。
- DeepSeek 是正文、规则上下文、附件解析结果汇总后的邮件级结构化文本 Provider；Qwen 是附件级 Provider，文本类附件使用本地抽取结果，图片和扫描 PDF 使用视觉解析。
- 通过预检查的邮件必须完整归档 raw EML 和全部附件后才能正式入库；三个入口已执行该硬规则，后续修改必须保留失败阻断测试。
- 装饰性内嵌图片在归档前剔除，不创建独立 OSS 对象、附件记录或 Qwen 调用；原始 EML 仍原样归档。HTML 表格属于正文，不拆成独立附件对象。
- 回复草稿创建不改变工单为 `auto_replied`；不可自动发送时进入或保持 `manual_review` 并只创建 `reply_review`，SMTP 成功后才以 `reply_sent` 转为 `auto_replied`。
- `unknown`、低置信、疑似业务邮件不得在预筛阶段丢弃，必须继续进入 OSS/入库/人工审核路径。
- IMAP 默认只读拉取：`UNSEEN + BODY.PEEK[]`，不标记已读，不移动邮件；SMTP 白名单仍是硬安全边界。
- 邮件中心的“立即捞取”仅向 operator/admin 展示，调用 `POST /emails/fetch/jobs`。
- SQL Server 中转适配器已经实现配置驱动的 ODBC 精确 SN 查询、增量/全量镜像同步和工单快照写出，默认 `disabled`；配置未完整时不得执行 ODBC 或任何外部网络访问。表模式生产启用前必须修复并验证同一 `ticket_no` 新版本的 UPDATE/MERGE 语义。

## 16. 2026-07-16 业务安全基线

以下规则优先于本文较早章节中的旧描述：

- 固定顺序为 `EML 导入 → 线程聚合 → 解析/人工修正 → SN 核心校验 → 其余安全校验 → ready_for_export → SAP submitted/accepted/rma_received → RMA 模板原链回复 → rma_sent → PDF/出站 EML 归档核验 → closed`。
- `POST /tickets/{id}/validate-sn` 只完成 SN 第一阶段，不得直接进入 `ready_for_export`；只有 `validate-export` 可以执行完整闸门。
- SN 校验必须基于 `sn_assets` 的存在性、有效状态、客户、物料和保修日期证据。SQL Server 关闭时只读本地镜像。
- `ready_for_export` 表示不可变输出快照已通过全部检查；通用状态流转、自动解析和人工任务都不得绕过完整闸门。
- 新 RMA 授权表统一使用与参考样例标题、页眉和两页结构一致的双语版本 `rma_authorization_v3_2_reference`；国内外布局一致。旧 `rma_authorization_auto_v3_1` 仅作历史证据，不得用于新签发。
- RMA 只为客户新报修首次生成。普通回复、补充、内部转发和收货事件不会重复生成。
- SMTP 最底层发送前必须再次验证登录账号等于 From、精确白名单、RMA 单一 To、空 Cc/Bcc；不确定发送结果不得自动重试。
- Miya 负责中文、Demi 负责英文、未知语言由 Miya 兜底；后续邮件继承负责人。负责人不是数据权限边界。

## 17. 2026-07-20 邮件与闭单新基线

- 邮件线程只允许 `References/In-Reply-To → Message-ID` 精确关联；归一化主题仅用于搜索和展示，禁止自动或人工合并工单。
- 客户必填字段由 `intent_type` 决定。新报修必填客户名称、联系人、客户邮箱、报修日期、寄回地址、故障描述和至少一条有效 SN；电话选填，客户编码及物料优先由 SN 主数据补全。
- 发送开关拆分为普通回复、缺失必填字段自动追问、自动附带 RMA PDF。普通回复是主控，RMA 开关不得独立发送邮件。
- 所有 SMTP 路径固定为测试邮箱单一信封；开启任一发送开关必须同步通过 IMAP 只读、SMTP 登录/NOOP 和离线 RMA 预检。
- `device_intake_received` 表示待修设备到达/入库，只作为 THIRD 生命周期邮件留存，不推进或关闭工单。
- 追问次数只按成功发送的 `missing_fields` 回复计数；草稿、RMA 和其他非追问回复均不计数。
- 当前代码种子没有合法的 `manual_review → closed / manual_close` 迁移；测试库残留旧规则不得视为正式能力。人工复核不得直接关闭，取消、误报等业务需单独设计终态。
- `AUTO_FOLLOWUP_ENABLED` 当前不是完整的定时自动催补能力；在周期扫描和入队生产者落地前，不得据此承诺多轮自动催补。
- 仓库和 Git 历史不得保存任何真实测试或生产凭据；发现凭据时按已泄露处理，先轮换再清理历史。

## 2026-08-03 安全、权限与数据语义基线

- 生产环境必须显式配置非占位的数据库口令、至少 32 字符的 JWT 密钥、强管理员初始密码、精确 CORS Origin 和 Trusted Host；不满足时应用拒绝启动。
- 浏览器会话使用 `HttpOnly + SameSite=Strict` Cookie；前端不得把 JWT 写入 localStorage/sessionStorage，旧 `repair_mail_token` 启动时立即清除。
- 角色固定为 `operator/admin`。operator 是所有业务接口的基础角色；admin 额外管理用户、配置和全局数据，并可查看所有用户的通知中心与站内消息。
- 板卡字段固定使用 `board_code/board_name`；SAP 物料字段固定使用 `material_code/material_name`，禁止在新接口和页面中互作展示别名。
- 同名技术状态必须按业务上下文显示：人工任务 pending=待分配、SAP pending=待提交 SAP、RMA pending=待生成 RMA、地址匹配 pending=待匹配。

## 2026-08-12 金标回归与工单终态修订

- `contact_phone` 与寄回联系人、寄回地址一样，是 `new_repair` 进入 SAP/RMA 闭环的客户必填字段；解析缺失时必须在首次追问中提出，不得拖到导出安全闸门才失败。
