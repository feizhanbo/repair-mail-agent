# 重构实施进度与回归记录

更新时间：2026-08-13

## 1. 当前发布结论

本轮完成了审计、目标设计、LangChain 统一模型层、附件标准化、无副作用 Shadow Graph，以及可恢复 Active Graph。Active Graph 已覆盖确定性校验、SAP 提交/不确定结果对账/轮询、RMA 准备、SMTP、归档关单、普通回复准备/发送和统一人工 Interrupt/Resume。

当前默认配置仍为 `WORKFLOW_ENGINE=legacy`。`shadow` 可在受控环境采集新旧差异；`langgraph` 模式已具备代码入口，但生产启用前仍必须完成 MySQL migration、独立 PostgreSQL Checkpointer 初始化、真实基础设施的重启恢复测试和金标灰度签收。未执行这些部署动作时不得直接生产切流。

## 2. 已完成阶段

### Phase 1：LangChain AI Gateway

- LangChain/LangGraph 升级并锁定到当前兼容版本。
- DeepSeek、Qwen、Qwen-VL 通过 LangChain `ChatOpenAI` 兼容模型和 `with_structured_output` 调用。
- 新增统一 ModelSpec、Structured Gateway、错误映射、usage/trace 提取。
- 删除 Provider 内部手工 HTTP 请求和 `json.loads(model_text)` 解析路径。
- 保留原 Provider 类作为兼容 façade，现有 Service 接口未破坏。
- 新增 AI 架构静态契约：厂商模型 SDK/`ChatOpenAI` 构造只能出现在 Model Factory，`with_structured_output` 只能由 Gateway 持有，Provider 禁止原始模型 HTTP endpoint 和响应 `json.loads`，防止后续重新散落调用。
- 新增严格 opt-in 的真实模型集成探针：仅当 `RUN_REAL_AI_INTEGRATION_TESTS=1` 且 DeepSeek/Qwen/Qwen-VL 配置完整时，用固定合成文本与 1×1 PNG 串行验证三类 structured output、trace 和 latency；默认不会联网或产生模型费用。

### Phase 2：附件标准化

- 新增独立 FileTypeDetector、NormalizedAttachmentContent 和 `attachment-parse-v2` Schema。
- 二进制解析先于模型调用；PDF 先检测文本、页数、表格和页面图片，扫描件或混合图文才转视觉，纯文本/表格保持文本路径。
- DOCX 确定性提取段落、表格和内嵌图片；只有实际含图时才调用 Qwen-VL，并携带已提取文本/表格上下文。
- 新增只检查不解压的 Archive SafetyInspector。
- ZIP/RAR/7Z/TAR/GZIP 先执行元数据安全检查；路径穿越、链接、损坏、加密、重复成员、成员/展开大小和压缩比超限会进入人工。
- 安全压缩包受限解包后递归遍历，子文件进入现有确定性 Parser Router；文本内容可按需进入 Qwen，图片/扫描 PDF 才进入 Qwen-VL。嵌套深度、全局成员数和总展开大小有固定预算。

### Phase 3：Shadow LangGraph

- 新增 TypedDict Graph State，未把 ORM 或 Session 放入 State。
- Runtime Context 注入只读 Snapshot Loader 和可替换 AI/Service 回调。
- 节点与 Conditional Router 覆盖加载、正文规范化、附件、分类、业务上下文和验证计划。
- Shadow Graph 到验证计划为止，不修改工单、不创建人工任务、不调用 SAP/RMA/SMTP。
- `WORKFLOW_ENGINE=shadow` 时在 legacy 完成后运行；失败被隔离，legacy 始终为业务事实。
- 对照结果写入现有 SystemEventLog，不提前固化新的 comparison 表。

### Phase 5/6 基础：HITL 与持久化

- PostgreSQL `AsyncPostgresSaver` 工厂与 Windows 可运行的 psycopg binary 依赖已配置。
- Docker Compose 已增加带 `langgraph` profile 的独立 PostgreSQL 16 checkpoint 服务、持久卷和健康检查；legacy 部署不启动它，Graph 切换前由 setup/audit 门禁验证。
- `LANGGRAPH_STRICT_MSGPACK` 已成为真实 Settings 字段，并显式配置 `JsonPlusSerializer(pickle_fallback=False)`；不再依赖被忽略的环境变量。
- Graph 模式启动时强制要求 PostgreSQL checkpoint URL，并拒绝业务 MySQL URL；独立初始化命令为 `python -m tools.setup_langgraph_checkpoint`。
- 新增 `python -m tools.audit_langgraph_release` 发布审计；可用 `--probe-local-test-checkpoint` 对 localhost `*_test` checkpoint 执行只读 schema/connectivity 探测。
- Graph 模式发布审计还会只读检查业务 MySQL revision 必须为 `r5m0h1c2d3e4`，并确认 workflow execution/interrupt 的 checkpoint identity 列存在；migration 未执行时部署脚本在启动应用前失败。legacy 模式不增加该数据库依赖。
- 新增显式 opt-in PostgreSQL 集成测试，验证跨连接、跨 Graph 重编译的 interrupt/resume 与已完成节点不重放；默认环境不会连接数据库。
- 同一集成文件新增严格双数据库场景：只接受 localhost PostgreSQL `*_test` 与 MySQL `repair_system_test`，跨连接重新编译 Graph 后，验证 MySQL execution/interrupt 与 PostgreSQL checkpoint 在等待态、恢复态和完成态一致，且 prepare 节点不重放。
- 使用当前 LangGraph `interrupt()` 和 `Command(resume=...)` API。
- 人工 `validate` Resume 会把当前 `task_id` 作为 `resolving_task_id` 传给确定性校验 Service，清理该任务已解决的 `missing_fields/conflict_fields`；自动初次校验及其他动作保持 `None`，避免误清业务标记，也避免人工放行后在 RMA PDF 门禁被历史标记再次拒绝。
- 人工任务在 interrupt 前由现有 Service 幂等创建；Resume 不重复创建。
- `workflow_interrupts` 记录产生 interrupt 时的 PostgreSQL `checkpoint_id`。Resume 前先对账当前 checkpoint：未前进才注入 `Command(resume)`；若 PostgreSQL 已前进而 MySQL ledger 提交丢失，则仅同步执行/interrupt 账本及下一 interrupt，禁止重放旧人工结果。
- ledger 同时记录 LangGraph checkpoint `step`。只有当前 checkpoint ID 非空、与原 ID 不同且 step 严格递增时，才认定上次 Resume 已推进；checkpoint 缺失、顺序不可验证或 step 回退均 fail-closed，交给 Job 重试/人工恢复。
- execution 现同步保存最新 checkpoint ID/单调 step。`graph_start` 重试遇到 `waiting_human`、`waiting_external`、`resume_queued` 或 `completed` 时，不再只返回 MySQL 摘要：必须逐项核对 PostgreSQL checkpoint ID/step、execution identity、next/interrupt 形态，以及 MySQL interrupt ID/status/checkpoint。缺失、回退、未入账前移、同 step 分叉或账本冲突均 fail-closed，且不会继续调用 Graph 或覆盖 `resume_queued`。
- 已完成 execution 的重复 Resume 同样先核对 checkpoint 与 active interrupt 账本；无法证明完成状态时拒绝幂等返回，避免 checkpoint 丢失后掩盖恢复故障。
- `graph_resume` 的确定性终止失败会释放 `resume_queued` 租约：interrupt 回到 pending、execution 回到 waiting 状态，人工 task 重新开放；原结构化决定保留在 ledger，不丢失审计证据。Graph Job 的 worker 租约过期属于“旧执行是否仍存活未知”，不会自动重放或开放第二次 Resume，而是进入显式人工恢复。
- 人工重新提交可复活同一幂等 Job 并增加有限 attempt 预算；scheduler-owned 外部 interrupt 只能由管理员通过显式 retry API 复活，人工 interrupt 禁止走该入口。
- Resume payload 校验 task_id 和 expected ticket version 字段。
- 新增最小 MySQL `workflow_executions` / `workflow_interrupts` 关联表；checkpoint 内容不写 MySQL。
- execution 对邮件、工单、触发 Job 的审计关联，以及 interrupt 对人工任务、恢复人的关联均使用 `ON DELETE SET NULL`，避免新增审计表阻断现有物理删除 API；删除 execution 时仍级联删除其 interrupt。
- 发布 schema 审计已覆盖两张 workflow 表的列、唯一约束、外键名称和 `ON DELETE` 动作；离线全迁移 SQL 测试也会检查这些 DDL，防止 ORM 与 migration 漂移。
- 显式 opt-in 的 MySQL 删除集成测试已加入真实 FK 场景：删除邮件/工单/人工任务后 execution/interrupt 必须保留，相关业务外键必须置空。当前主机无测试 MySQL，场景尚未实际执行。
- migration head：`r5m0h1c2d3e4`。

### Phase 4/7 基础：确定性校验与 SAP slice

- Graph 只调用现有 Validation/SAP Service，不复制 SN、客户、政策、SQL Server 逻辑。
- Validation DTO 增加向后兼容的 `sap_required` 和 `export_id`。
- `ready_for_export` 且无需 SAP 时不误提交。
- `waiting_sap_result` 进入外部等待；`submit_unknown` 只调用 reconcile，不重复提交；明确失败转人工。
- 对账确认远端不存在后，`pending` 允许回到 `submit_sap` 做一次安全重提；State 记录 `sap_submit_attempt_count`，第二次仍为 `pending` 时强制转人工，避免 Graph 无界自循环。
- 安全重提计数同时绑定 `sap_submit_export_id`；人工 reparse/重新校验生成新 export 后计数从 1 重新开始，不继承旧 export 的尝试次数。
- `poll_sap` 的 `submit_unknown → reconcile → pending` 路径已纳入同一有界重提规则：首次确认远端不存在时最多回到 `submit_sap` 一次，达到上限转人工。Graph adapter 同时关闭 poll 内部 reconcile 的 legacy Job 调度及 RMA Job 调度，避免 Graph execution 与旧 worker 对同一 export 双提交/双轮询；legacy 调用保留默认调度行为。
- `submit_export_batch`、`reconcile_uncertain_submission`、`poll_export_batch` 增加默认兼容的内部调度开关；Graph 路径关闭旧 Job，避免双轮询/双提交。

### Phase 7/8：RMA、SMTP 与回复闭环

- RMA 生成与 SMTP 发送拆为 `prepare_rma_authorization` / `send_prepared_rma_authorization`；旧公开入口默认行为不变。
- 普通回复拆为 `create_reply_draft(send_immediately=False)` / `send_prepared_reply`；Graph 中准备与发送为两个节点。
- 普通回复准备结果已在 Active Workflow adapter 统一为顶层 `status/reply_id/send_status` 契约，兼容新建草稿与幂等复用草稿的真实 Service 返回形状；Router 不再依赖测试专用的多层 `reply.reply.send_status`。`pending_review` 保留 `reply_id` 进入 HITL，人工可批准/拒绝；`approved_pending_send` 才进入发送节点。
- RMA SMTP 成功与归档关单通过 `finalize_rma=False` 分开，归档节点复用 `retry_rma_archive`。
- SMTP 继续使用稳定 Message-ID、`reply:{id}:smtp` 外部操作账本；`send_uncertain` 禁止自动重发。
- SAP 等待使用持久化 Interrupt，不在 worker 内 sleep；后台 `graph_resume` Job 根据 `next_poll_seconds` 唤醒。
- 人工审核任务与 `workflow_interrupts` 绑定；人工任务 resolve、回复 approve 两类 API 均排队 Resume。
- Graph Resume 路由支持重新校验、重新解析/退出旧执行、追问、批准发送和关闭。

### Phase 4/8：Active 入口

- `WORKFLOW_ENGINE=langgraph` 时，现有成熟解析/结构化结果应用和工单落库继续作为迁移期 Service。
- 旧解析器不再执行校验/追问草稿等下游编排；投递幂等 `graph_start` 后由 Graph 接管。
- `graph_start` / `graph_resume` 均走现有持久化 Job 队列，默认 legacy 不受影响。
- 每次 Job claim 生成唯一 fencing token；heartbeat 只为仍匹配 token 的 `running` Job 续租，旧 worker 在业务执行前和最终落账前均核验 owner，丢租约后取消并 rollback，禁止覆盖新 owner 状态。
- `ASYNC_JOB_STALE_SECONDS` 最小为 30 秒，heartbeat 在 stale 窗口内至少有三次续租机会。普通 Job 维持 stale 自动恢复；`graph_start` / `graph_resume` 因 checkpoint 并发风险 fail-closed 到 `needs_manual_review`。
- 管理员只能通过 `POST /api/v1/jobs/{job_id}/retry-stale-graph` 恢复 stale Graph Job，且必须明确确认旧 worker 已停止；确认人、时间和脱敏原因写入审计，未确认返回冲突。
- MySQL 只保存执行/Interrupt 业务索引，完整 Graph State 只存 PostgreSQL Checkpointer。
- 生产 `active_graph.py` 现在只保留一个权威 `build_active_email_ticket_graph`；早期 validation/SAP 迁移切片已移入测试夹具，业务运行时无第二张 Active Graph 可误用。
- 新执行写入 `workflow_version=langgraph-v2`；State schema 保持 `email-ticket-state-v1` 兼容旧 checkpoint。`execution_id` 对 workflow、graph thread 和 source email 的绑定不可变，身份冲突直接拒绝。
- 金标工具在 `langgraph` 目标运行时会逐封采集脱敏 execution/checkpoint/interrupt 证据；缺少 v2 ownership、checkpoint identity、合法稳定状态或存在错误时整例失败。多轮补充邮件会分别核验原始邮件与 supplement execution。
- 金标 reset 计划显式纳入 workflow execution 与 Graph thread；仅在现有 localhost 测试库门禁下先删除并验证指定 PostgreSQL thread，再级联删除 MySQL execution/interrupt，最终同时核验邮件、fetch、execution 与 checkpoint 均无残留，支持可重复回归。

## 5. 回滚

- 保持或恢复 `WORKFLOW_ENGINE=legacy`，即可停止新 Shadow/Graph 执行。
- Shadow 不产生业务副作用，不需要业务补偿。
- 已执行 migration 时可回退 `r5m0h1c2d3e4`，但必须先确认不存在需恢复的 workflow execution/interrupt 记录。

- 已成功或结果不确定的 SAP/SMTP 操作禁止通过 legacy 重做，只能沿原 Service 对账/恢复。

## 6. 2026-08-12 增量收口：权威入口、异常边界与执行状态

- `WORKFLOW_ENGINE=langgraph` 不再先调用 `reparse_email()` 完成旧编排；入口只投递 `graph_start`，Graph 从 `prepare_email_parse` 开始接管解析、AI 候选、采纳、校验及后续副作用编排。
- 从原长函数提取并复用 `prepare_email_parse_context`、`generate_email_ai_candidate`、`adopt_email_parse_candidate/adopt_email_parse_context`。旧链仍走同一业务 Service，新链不复制业务规则。
- 人工 API 对已绑定 Graph interrupt 的任务只记录结构化决定并排队 Resume；业务修改、状态转换和重新校验由 Graph 继续编排，消除了 legacy resolve 与 Graph resume 双执行。
- 可由操作员修正的 HTTP 4xx（排除 408/425/429）、`ValueError`、`LookupError` 统一映射为 State 的 `error.code/stage/retryable/recoverable` 并进入 HITL；系统异常继续交给持久化 Job 重试。
- 活动流程新增 `workflow_outcome`，不再用 `shadow_completed` 表示真实执行终态。追问发送后结束本次 execution；工单的等待客户状态仍由业务数据库表达。
- 活动 Node 的 MySQL 业务事实在 Node 返回前提交，随后 LangGraph 才写 PostgreSQL checkpoint；提交失败先 rollback。反向的“业务已提交、checkpoint 未写”窗口通过 Service 幂等键安全重放，避免 checkpoint 越过未提交事实。
- SAP/RMA 外部等待和人工审核测试已在每次 Resume 前重新编译 Graph，只复用 checkpointer，覆盖进程重建后的恢复语义。
- 灰度入口支持 `LANGGRAPH_EMAIL_ALLOWLIST` 与 `LANGGRAPH_ROLLOUT_PERCENT`；非 allowlist 邮件按 email ID 稳定分桶，同一邮件的重试不会跨引擎。
- 灰度期间回复审批按实际 pending workflow interrupt 判断归属，而不是只看全局开关；未命中 Graph 的 legacy 回复继续走原发送链。
- 人工任务同样按实际 interrupt 绑定决定由 Graph Resume 或 legacy Service 接管；未绑定任务保留 SAP 下游调度，避免全局 Graph 开关造成无人编排。
- 规则/AI ParseResult 通过 Graph execution marker 复用，采纳节点通过 adoption marker 避免重复版本更新/工单写入，普通回复复用待审或已自动批准但未发送的草稿。

## 7. 2026-08-13 增量收口：HITL 所有权与邮件级单活执行

- Human interrupt 暴露的动作现在根据 State 上下文生成：无工单时不会宣称可执行校验/追问，无待发送回复时不会宣称可批准或拒绝发送。Resume payload 必须属于 interrupt 当时公布的 `allowed_actions`，否则 fail-closed。
- 已绑定 `WorkflowInterrupt` 的人工任务和回复，在 `pending` 与 `resume_queued` 两种状态下都始终归 Graph 所有。重复提交、专用 reparse、批准及拒绝不会回退到 legacy Service；拒绝也会排队 Resume，让原 checkpoint 走确定性终止路径。
- `apply_human_decision` 将确定性 Service 返回值并入 State，Router 只根据已落地结果路由，不在 Node 内隐藏后续流程。
- `dispatch_email_parse` 在 Graph 模式下先锁定 Email 行，再检查同一邮件的活跃 `WorkflowExecution` 和尚未创建 execution row 的 `graph_start` Job。发现 `running`、人工/外部等待、Resume 排队或活跃启动 Job 时复用当前所有者，不再生成第二个随机 execution。
- `needs_manual_review` 的 stale `graph_start` 和普通终止失败的 Graph 继续占有邮件，防止新 reparse 绕过恢复门禁或在“外部成功、checkpoint/落账失败”窗口重复副作用。管理员可复活同一个失败 `graph_start` Job；完成或取消的记录不占有邮件，显式重新处理能力保持不变。
- Graph 启动时将 `JobRunLog.id` 写入 `WorkflowExecution.trigger_job_id`；已有 execution 只允许补写相同 Job 身份，不同触发 Job 尝试复用 execution id 时 fail-closed。

### MySQL 同邮件并发派发探针

- 新增严格 opt-in 的 `tests/test_email_dispatch_integration_mysql.py` 与审计参数 `--probe-local-test-email-dispatch`。
- 探针只接受 localhost `repair_system_test`，使用两个真实 AsyncSession：首事务锁定合成 Email 并创建 `graph_start`，第二事务必须在首事务提交前阻塞，提交后必须复用相同 execution ID 与 Job ID，数据库中最终只能存在一个启动 Job。
- 探针不会运行 worker、Graph、模型或外部 Service；必须在没有后台 worker 的独立测试库运行，结束后按测试 Email/Job 精确清理。
- `local_graph_release_gate_passed` 现在要求 Graph 模式下 checkpoint、Job lease、email dispatch 三个本地探针全部执行成功；该字段仍不能替代真实外部系统、金标、业务签收和灰度验收。
- 发布证据格式已升级为 schema v2，消费方必须识别第三探针；失败启动 Job 的管理员恢复还会核对 Job 类型、email 资源、execution mode/email/trigger Job/status，任一冲突均拒绝复活。相同 Job 真正开始恢复时，execution 从 `failed` 明确回到 `running`，并继续原 checkpoint。
- `deploy.sh` 不再把“不请求探针但退出 0”的配置审计误当作 Graph release gate。Graph 模式必须先验证同一 clean commit 生成的 schema v2 三探针 JSON 与 SHA-256 sidecar；证据通过只读 `release-evidence/` 挂载提供，验证发生在 checkpoint 初始化之前。旧 commit、dirty 来源、篡改、探针缺失或 gate=false 均 fail-closed。
- 已失败 execution 如果 PostgreSQL 中没有任何 checkpoint，不得重新注入初始 State 从头执行；恢复会报 `WORKFLOW_CHECKPOINT_MISSING` 并保持 failed，避免无法证明前次副作用状态时盲目重放。
- 部署证据进一步限制为 168 小时内生成，并验证解析后的 JSON/sidecar 仍位于只读可信根，拒绝未来时间和路径/符号链接逃逸；证据限定 CLI 参数脱离 verify 模式或最大年龄非正数时也会直接报错。
- 证据验证逻辑已从运维工具下沉到可复用 `app/services/release_evidence.py`。FastAPI lifespan 在所有 runtime config、RMA 和 scheduler/Job worker 初始化之前执行同一门禁；因此绕过 `deploy.sh` 直接启动容器也不能启用未经验证的 Graph。`deploy.sh` 导出当前 `APP_RELEASE_COMMIT`，Compose 注入进程；其他编排平台必须注入镜像对应 commit。
