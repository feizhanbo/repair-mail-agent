# 邮件报修自动化系统详细开发细节文档

## 2026-08-20 现行唯一邮件入口

1. IMAP、JSON、EML 及异步入口统一执行：幂等台账、自发/收件人/重复预检、规则候选、RFC 线程摘要、轻量分类、必要附件证据、分类持久化路由。
2. FIRST 完整归档并进入字段抽取/Ticket/Workflow；SECOND 和 UNKNOWN 只保存 minimal Email、raw EML、附件 metadata 和邮件级人工任务；THIRD 只保存台账与可选线程锚点。
3. 重解析只执行 `field_extract`，不得重新分类；UNKNOWN 只能通过 `promote_to_first` 明确选择 FIRST 意图并锁定晋升。
4. 系统自发邮件按 From、Sender、系统地址集合和已归档 SMTP Message-ID 过滤，`rma_sent` 是工作流状态而不是客户邮件意图。

## 2026-08-20 配置、删除与页面交互实现

1. `runtime_config` 启动时从 `system_configs` 读取并刷新进程缓存；表为空时可一次性迁入旧 JSON，后续写入只更新数据库。调度执行前刷新邮件拉取配置，保证多进程最终读取同一持久化事实源。
2. `/system/config` 管理业务与邮件拉取配置；`/system/sn-sync/config` 管理 SN 同步配置。SN 分区允许 operator/admin，其他系统配置仍限 admin。SN 资产页调用同一 `/system/sn-sync` 作为快捷入口，不复制配置表单。
3. 删除和配置变更请求不接收用户 reason。后端以目标、影响范围和变更字段生成审计描述，前端用中文表格展示变更前后、影响数量、阻断项、OSS 影响和不可逆结果，再二次确认。
4. 邮件手工 JSON/EML 导入和邮件导出 API 为兼容接口并标记 deprecated，邮件中心不再展示对应按钮。邮件详情返回关联工单入口；工单时间线展示全部关联邮件入口。
5. 内部 `thread_id/thread_key` 继续用于 RFC 关联和服务查询，但不在邮件/工单用户界面展示。`intent_subtype` 已从 schema、服务、数据库及界面移除，顶层分类逻辑不变。
6. AI 日志、SN 字段映射及配置/删除影响默认使用中文表格；原始 JSON 只放在折叠的“技术详情”中，不作为用户理解业务结果的唯一方式。

## 2026-08-14 模板组合与补充邮件恢复细节

1. 内容模板先渲染业务正文；无专用 HTML 时从纯文本安全转换 HTML；随后无条件组合对应语言的基础模板，确保追问和 RMA 都带完整 Miya/Demi HTML 签名。
2. HTML 基础模板引用 `cid:accotest_logo`，MIME 构建阶段嵌入项目内置规范 PNG。检查内联资源必须遍历完整 MIME 树，不能只使用会排除 related 部件的附件迭代接口。
3. 若客户补充引用的系统追问 HTML 包含已知 `accotest_logo`，而收件箱保存的父 EML 未携带该 related 部件，渲染器使用同一内置规范 Logo 恢复；未知 CID 缺失或一对多冲突仍阻止发送并转人工。
4. 国内模板选择以工单请求日期逐 SN 判断保修；全部在保或全部超保才可自动选择，混合/缺失/冲突进入人工。英文正文使用海外英文返回地址，不把国内中文维修地址注入业务正文。
5. 客户补充回归邮件必须从 rmatest2 对系统追问执行真实 Reply 结构，包含 `In-Reply-To`、累积 `References`、纯文本 `>` 引用和 HTML `blockquote`；解析仅采纳最新补充段。

## 2026-08-12 富文本回复渲染与恢复

1. `MailReplyRenderer` 下载直接父邮件 `raw_eml_oss_object_id`，用 RFC822 MIME 解析得到根 HTML；没有 HTML 时从根 `text/plain` 转义生成降级 HTML。
2. 清理主动内容后，只扫描 `src/background/href` 与 CSS `url(cid:...)`。匹配的 MIME Part 即使声明为 attachment 也作为 related 资源复制；未引用的历史图片、Excel、PRC、PDF 均排除。
3. CID 按父邮件 ID、原始 EML SHA 和资源序号确定性重映射。缺失返回 `REPLY_PARENT_CID_MISSING`，一对多返回 `REPLY_PARENT_CID_CONFLICT`，原始 EML/OSS异常使用对应 `REPLY_PARENT_*` 错误码。
4. `thread_history_hash` 保存父邮件 EML、清理后正文、CID 映射和资源哈希的快照；发送守卫重新计算快照，不一致返回 `REPLY_THREAD_HISTORY_CHANGED_REGENERATE_REQUIRED`。
5. MIME 为 plain/html alternative，HTML 与CID资源组成 related，RMA PDF再作为根层新附件。归档字节和SMTP发送复用同一 `EmailMessage`，避免二次组装产生不同边界或CID。
6. 渲染失败创建 `reply_render_failed` 或 `rma_reply_render_failed` 人工任务；修复父邮件归档或CID根因后重新生成草稿，禁止绕过模板与线程门禁。

## 2026-08-11 分层分类执行链

1. 规则层只产生确定性字段候选和审计证据；前置分类 AI 使用严格 13 类 Enum 输出 `intent_type`、`handling_level`、候选意图、证据和置信度。
2. 程序在分类前构造 `Message-ID/In-Reply-To/References`、线程、当前工单类别/状态/RMA/SN 上下文；最终分类只来自严格 AI 契约或人工锁定，不再由 `_contextual_intent()`/规则覆盖。
3. FIRST 才能进入字段合并、完整性、安全闸门、SAP 与 RMA；补充邮件仅在当前标准工单处于等待资料上下文时合并，否则转 `repair_thread_other`。
4. SECOND 只创建邮件级人工任务和通知；即使同线程已有活跃 FIRST，也不得创建 side-car/旁路工单或进入 FIRST Workflow。旧 `create_manual_business_ticket_from_email()` 已删除。
5. THIRD 结束本封自动处理，可通过 `lifecycle_event` 关联历史工单，但不改变工单状态。UNKNOWN 创建带原因、恢复节点和邮件上下文的人工任务。

### API 与恢复入口

- `GET /api/v1/emails/classification-catalog` 返回当前四层十四类目录；邮件列表/导出支持 `handling_level` 筛选。
- 人工任务 `claim/assign/release/resolve` 为现行入口，不再返回“分配功能禁用”。邮件级任务允许 `ticket_id=NULL`。
- SECOND 不存在旁路工单；邮件级人工任务直接记录处理结论，不调用 SAP/RMA。

### 闭单事实门禁

RMA 回复 SMTP 必须明确成功，保存服务端 Message-ID，RMA PDF 和出站 EML 均成功归档，且模板/线程/归档事实复核通过后，才允许 `rma_issued_and_archived` 把标准工单置为 `closed`。任一外部结果失败或不确定都保留可恢复节点，不得用通用状态接口绕过。

## 2026-08-11 删除 API 与恢复接口

所有接口要求 admin 登录；DELETE 的 `reason` 长度为 3–500，`confirmation_token` 必须来自同一用户、同一对象最新预览且 10 分钟内有效。

| Method | Path | 说明 |
| --- | --- | --- |
| GET | `/api/v1/emails/attachments/{id}/delete-preview` | 附件影响与 OSS 引用预览 |
| DELETE | `/api/v1/emails/attachments/{id}` | 删除附件直属解析/AI 数据并补偿清理 OSS |
| GET | `/api/v1/emails/{id}/delete-preview` | 邮件、附件、线程、工单关联和阻断预览 |
| DELETE | `/api/v1/emails/{id}` | 删除邮件直属数据；非关键工单关联解除，关键邮件拒绝 |
| GET | `/api/v1/tickets/{id}/delete-preview` | 工单聚合、外部影响、任务和 OSS 预览 |
| DELETE | `/api/v1/tickets/{id}` | 删除工单聚合但保留邮件 |
| GET | `/api/v1/deletion-operations/{audit_id}` | 查询数据库删除和 OSS 补偿状态 |
| POST | `/api/v1/deletion-operations/{audit_id}/retry` | 手工重试 OSS 删除 |

- 正常完成返回 200；数据库已删但 OSS 待重试返回 202。不存在返回 404，陈旧/错误令牌或业务阻断返回 409，生产环境强制删除返回 403，参数错误返回 422。
- `force_local_cleanup` 只存在于邮件/工单接口，只能在 `APP_ENV=dev/test + repair_system_test` 使用；邮件必须满足测试信封，含 SAP 导出的工单还要求 `RELAY_ADAPTER=test_http`。运行中或不确定外部操作永远不能强制绕过。
- 排队/等待重试任务会标记 `superseded/RESOURCE_DELETED`；运行中任务阻止删除，避免删除后 worker 写回。补偿任务失败写入明确错误码、恢复阶段和下次运行时间。
- DELETE 事务先对 Email、Attachment 或 Ticket 主行执行 `SELECT ... FOR UPDATE`，然后在锁内重新计算预览并校验确认令牌，防止 worker 在“复核通过”和“真正删除”之间改变状态。

## 2026-08-05 入站和回复实现细节

1. 常规 IMAP UID 搜索增加 `NOT FROM <IMAP_USER>`；按 Message-ID 的恢复搜索不裁剪候选，但原始 EML 解析后仍执行相同收件人门禁。
2. 原始 EML 解析 `To/Cc/Delivered-To/X-Original-To`。目标账号不在任一收件头时以 `RECIPIENT_NOT_TARGET_MAILBOX` 终止；发件人为目标账号时以 `SELF_SENT_MAIL_SKIPPED` 终止，均不建工单。
3. 回复父邮件只能是同工单、同线程的入站邮件。`In-Reply-To` 指向该父邮件，`References` 合并父邮件已有链、父邮件的 `In-Reply-To` 和父 Message-ID。
4. 历史正文只读取直接父邮件原始 EML 的完整 HTML，不遍历线程逐封拼接；附件仅复制 HTML 实际依赖的 CID 资源。出站归档只把新写内容存入 `latest_reply_segment`，用于业务解析而非回复渲染。
5. RMA 回复主题等于 PDF 文件 basename；追问等普通回复使用去除重复 `Re/Fw/Fwd` 前缀后的 `Re: 原主题`。两类主题均不改变 RFC 回复头。收货确认回复已下线。
6. 邮件生成 `multipart/alternative`，先写 `text/plain`，再写 `text/html`，RMA PDF 作为唯一新附件。SMTP 前校验缺失字段、线程版本、历史哈希、渲染哈希、主题规则和模板快照。
7. PDF 使用 FontTools 从配置的 CJK 字体按动态字段字符生成子集，再通过 PyMuPDF 嵌入；不允许整套 TTC 回退。结果超过 `RMA_PDF_MAX_BYTES` 时抛出 `RMA_PDF_TOO_LARGE`。
8. 出站 `Email.subject/normalized_subject` 必须保存实际 RFC822 传输主题（测试信封包含 `[TEST ONLY]`），`ReplyRecord.subject` 保留业务主题用于和 PDF basename 比较。E2E 断言必须读取 `email_timeline` 的出站记录，不得调用“自动补前缀”函数后做恒真判断。
9. 2026-08-05 真实样本暴露 `FOVIM812...` 边界问题：AI 将板卡尾部 `M` 吸收到板卡代码并导致 SN 少首字母。当前安全结果是 SN 主数据不命中并进入人工复核；下一轮应在候选归一化层结合已知板卡词和 SN 资产格式提出候选，但仍须主数据精确命中后才能自动采纳。

## 2026-07-31 字段对齐与自动/人工业务链路

确定性解析顺序如下：

1. AI/附件只抽取客户字段、SN、板卡编码/名称和故障信息，不把板卡写入 SAP 物料字段，也不把维修收件地址写入客户邮寄地址。
2. SN 校验按 `sn_assets.sn` 核对有效性、客户和 SAP 物料；仅当工单已有客户名称且与资产客户名称规范化后一致时，才自动补客户编码。SN 主数据不决定维修寄回地点。
3. 政策解析收集全部明细对应的 SN 资产，要求客户代码/客户名称一致、保修结论一致；客户代码确认后按客户代码和工单日期唯一命中启用政策，并要求该政策给出有效 `customer_scope`。无匹配、多匹配、范围未知、混合保修或人工政策均创建/复用人工任务。
4. 国内路线按 `board_code + board_name` 精确匹配；无精确名称时允许同一 `board_code` 的全部启用记录仅指向一个地点。仅名称、无板卡、跨地点冲突、地址不完整均为人工。海外路线只查询唯一启用的 `overseas + scope_default` 北京记录。
5. 完整安全校验要求政策已解析、`charge_status` 非人工、客户方地址/联系人/电话完整、SN/物料有效。维修寄回路线未解析不阻止 SAP 提交，但在 SAP 回填 RMA 后、生成 RMA 邮件前必须解析；否则转 `return_route_review` 人工任务。
6. SAP 导出行从工单读取客户方 `mailing_address/contact_person/contact_phone`，从明细读取 SN 与物料，并快照收费状态。RMA 模板从明细 `return_route_snapshot` 读取维修收件地址。

新增操作接口：

- `POST /tickets/{ticket_id}/policy/resolve`：重新执行客户范围与服务政策自动解析。
- `POST /tickets/{ticket_id}/policy/manual-override`：人工确认当前工单的 `customer_scope` 与 `charge_status`；写字段审计与政策快照，不修改客户政策主数据。
- `POST /tickets/{ticket_id}/return-routes/resolve`：重新匹配全部明细的维修寄回路线。
- `POST /tickets/{ticket_id}/items/{item_id}/return-route/manual`：人工选择北京或天津，要求该地点的启用收件资料唯一且完整，并写明细快照与审计。

主状态不新增。自动解析成功后仍由完整安全校验决定是否从 `parsed` 进入 `ready_for_export`；任何政策或客户范围不确定进入/保持 `manual_review`。SAP 子状态仍由 `ticket_relay_exports/export_sap` 表达；RMA 路线不确定发生在回填后时进入人工，不允许绕过后直接发送。

## 2026-07-30 RMA 签发、恢复与人工对账接口

- `POST /replies/{reply_id}/retry-archive`：仅允许已明确发送成功的 RMA 回复，恢复 PDF/出站 EML 归档和闭合核验；该路径不调用 SMTP。
- `POST /tickets/{ticket_id}/sap-export/reconcile`：按本批全部 SourceRequestID 重新核对未知提交；不接受人工填写远端标识。旧逐行 CallID 对账接口返回 `410 SAP_CALL_ID_RECONCILIATION_RETIRED`。
- `POST /tickets/{ticket_id}/rma/retry-send`：若已有 sent 回复，优先恢复归档且绝不重发；只有明确未发送时才创建新的 RMA 签发任务。
- `POST /tickets/{ticket_id}/rma/manual-policy-approve`：操作员核对特殊价格/币种/税率后写入不可变人工确认信息，仅生成待审模板草稿，强制禁止自动发送。匿名规则因固定 PDF 不适用继续阻止。
- 后台任务新增 `rma_archive`，稳定幂等键为 `rma_archive:{reply_id}`，最多三次退避重试。
- 工单详情返回 `rma_issue_summary`、回复归档字段和 `external_operations`；页面展示正式 RMA、PDF 校验、SMTP、Message-ID、PDF/邮件归档六个闭合闸门，以及 SAP 不确定提交人工对账入口。
- 已闭合工单后续入站邮件先形成带 predecessor 的新线程并执行规则/AI 分类；确定为新报修才创建新工单，其他结果按分类终止或进入有恢复方式的人工节点。

`tax_rate` 不传 SQL Server。表模式将一张工单全部 SN 使用同一事务参数化 INSERT，并按 SourceRequestID 批量轮询 `U_CustomerNum`。任务状态为：

1. 写入完成，记录 `submitted_at`。
2. SQL Server 事务提交成功，记录 `accepted_at` 并进入 `waiting_sap_result`。
3. 每 300 秒轮询；合法 RMA 后记录 `rma_received_at`。累计 8 个上海工作小时无结果则进入人工复核。

SAP 提交失败生成一次高优先级 `sap_export_failed` 通知；中转库整批事务提交成功后生成一次 `sap_export_accepted` 通知；RMA 模板邮件实际发送成功后生成一次 `rma_reply_sent` 通知。

接口：

- `GET /emails/export`
- `GET /emails/{email_id}`
- `GET /emails/{email_id}/flow-trace`
- `GET /emails/{email_id}/raw-eml-url`
- `GET /emails/attachments/{attachment_id}/download-url`
- `POST /emails/ingest`
- `POST /emails/ingest/jobs`
- `POST /emails/ingest-eml`
- `POST /emails/ingest-eml/jobs`
- `GET /emails/fetch-status`：operator/admin 读取服务端账号、轮询、批量、只读归档、最近及活动任务状态。
- `POST /emails/fetch/jobs`：前端唯一“立即捞取”入口；无参数时完全采用服务端 IMAP 配置，活动作业存在时复用。
- `POST /emails/fetch-now`：deprecated，仅保留 admin 诊断兼容。

- `POST /emails/{email_id}/reparse/jobs`

- `POST /email-threads/{thread_id}/split`

当前流程：

1. 手工 JSON、EML 文件或 IMAP 形成统一 `EmailIngestRequest`；raw EML 计算 SHA-256。
2. IMAP 入口先按 `mailbox_account + folder_name + imap_uid` 查 `mail_fetch_records`；全部入口再规范化 Message-ID 并查 `emails.message_id`。缺失 Message-ID 时由 raw hash 生成稳定替代值。
3. 归档前剔除装饰性 inline 图片，并执行完整规则候选解析：分类、字段、明细、缺失、冲突、置信度和证据一次生成。随后用扩展名、声明 MIME 和魔数识别压缩容器；ZIP、RAR、7Z、TAR、TAR.GZ/TGZ/GZIP 标记为不阻塞的工程辅助资料，但仍作为有效附件归档。只有明确无关且无业务/回复/有效附件信号才跳过整封邮件。
4. 通过预检后上传 raw EML 和全部有效附件到 OSS；任一失败不创建正式邮件。装饰图片不创建附件对象，但原始 EML 保持原样归档。
5. 全部对象成功后在正式事务写入线程、邮件、附件和预规则 `parse_results`；异步入口同时写初次 job 并复用该规则记录，显式“重新解析”才生成新规则记录。同步兼容入口调用相同 service。
6. DeepSeek 汇总正文、规则上下文和普通业务附件解析结果生成邮件级候选，随后自动采纳或转人工。工程辅助压缩附件只提供文件名、格式和已保存元数据，不进入 Qwen、多模态结果、字段候选或追问内容。

EML 前端导入规则：

- `EmailsPage` 固定调用 `POST /emails/ingest-eml/jobs`，上传完成后立即登记 job，由全局任务监视器轮询；同步接口保留给兼容和诊断使用。
- 导入请求超时为 600 秒；Nginx 关闭 API 请求缓冲并允许大于应用单附件限制的 EML 请求到达后端，由业务层按附件规则判定。
- 异步 worker 对每个附件阶段独立提交。重试时复用已归档 OSS 对象，并跳过 `parsed`、`skipped`、`skipped_decorative`、`unsupported` 终态，避免重复下载或调用模型。
- MySQL 模型启用 `eager_defaults`，确保 flush 后可直接读取 `created_at/updated_at` 等服务端默认值，不在异步上下文触发隐式 IO。
- 重新解析从原始 `text_body/html_body` 重建最新正文和历史对话，禁止使用上次已裁剪的 `clean_body` 覆盖历史 SN 等上下文。

手工 `/emails/ingest` 的 `attachments` 元素支持：

```json
{
  "file_name": "fault-report.pdf",
  "content_type": "application/pdf",
  "file_size": 1024,
  "content_base64": "<base64>"
}
```

导入结果可包含 `duplicate`、`skipped`、`email` 和 `precheck`；重复与高置信无关邮件必须在前端给出明确提示。

当前数据模型：

- 使用 `emails`，不是 `business_emails`。
- `mail_fetch_records` 已用于 IMAP UID 幂等和拉取审计。

异常要点：

- `EMAIL_NOT_FOUND`
- `EMAIL_THREAD_NOT_FOUND`
- `EMAIL_THREAD_SAME_TARGET`
- `EMAIL_THREAD_SPLIT_EMPTY`
- `EML_FILE_REQUIRED`
- `EML_FILE_EMPTY`
- `ATTACHMENT_CONTENT_INVALID`
- `RAW_EML_NOT_ARCHIVED`
- `ATTACHMENT_NOT_ARCHIVED`
- `OSS_OBJECT_NOT_FOUND`

现行一致性规则：三个入口共用强归档服务；OSS 未配置返回 `OSS_NOT_CONFIGURED`，原件或任一附件失败返回 `OSS_ARCHIVAL_FAILED`，均不得创建正式邮件。IMAP 失败 UID 写入退避时间并由后续调度重试。

测试要点：

- 重复 message_id 不重复入库。
- `In-Reply-To` 命中线程。
- 重复和高置信无关邮件不产生 OSS 对象或正式邮件。
- 缺失 Message-ID 的同一 EML 通过 raw hash 去重。
- raw EML 与每个正式附件均有关联的成功 OSS 对象。
- AI 不可用时生成人工复核。

## 6. AI 解析与解析结果采纳

后端：

- `backend/app/services/ai.py`
- `backend/app/integrations/ai_provider.py`
- `backend/app/api/v1/parse_results.py`
- `backend/app/services/tickets.py`
- `backend/app/models/parsing.py`
- `backend/app/models/logs.py`

前端：

- 邮件详情解析结果。
- 工单详情解析证据。
- `/ai-logs` → `AiLogsPage.tsx`

接口：

- `POST /parse-results/{parse_result_id}/apply`
- `POST /tickets/parse-results/{parse_result_id}/apply`
- `GET /ai-logs`

AI 调用规则：

- DeepSeek 是邮件级文本 Provider，只接收正文、规则候选和附件已经抽取的文本/JSON，不接收附件二进制。
- Qwen 是附件级 Provider：文本/表格类附件先本地抽取后调用 Qwen JSON；图片和无文本 PDF 使用 OSS 短期预签名 URL 调 Qwen VL。
- AI 必须输出 JSON。
- 使用 Pydantic 模型校验输出。
- 低置信、缺字段、冲突、AI 不可用进入人工复核。
- 自动采纳阈值由 `AUTO_APPLY_MIN_CONFIDENCE` 控制，默认 0.85；还必须满足无缺失、无冲突、关键附件成功且 SN 校验全部通过，否则创建或复用人工任务。
- 已关闭工单线程收到新邮件时不得自动修改关闭工单，必须创建人工判断任务。
- 数据库 `ai_call_logs` 只写摘要、错误分类、重试和 token usage。JSONL 保存完整文本 Prompt、请求、原始响应和解析结果，管理员通过 `GET /ai-logs/{id}/detail` 查看且产生操作审计；key、认证头、签名参数、data/base64 和二进制必须脱敏，默认保留 30 天。

统一附件解析矩阵：

| 类型 | 本地处理 | Qwen 输入 | 限制和结果 |
| --- | --- | --- | --- |
| `txt` | 多编码文本解码 | 截断后的文本 | 最大模型输入由 `ATTACHMENT_TEXT_MAX_CHARS` 控制 |
| `csv` | 最多抽取前 200 行 | 表格文本 | 长文本记录 `TEXT_TRUNCATED_FOR_MODEL_INPUT` |
| `html` | BeautifulSoup 转纯文本 | 截断后的文本 | 不执行脚本 |
| `docx` | 从 OOXML 提取段落 | 段落文本 | 损坏文件转人工 |
| `xlsx` | 最多 10 个 sheet、每表 200 行、40 列 | 表格文本 | 只读加载 |
| `image/*` | 不做本地 OCR | 30 分钟预签名 URL | Qwen VL |
| `pdf` | 前 15 页抽文本 | 文本或预签名预览 URL | 超页标记 `truncated=true` |
| ZIP/RAR/7Z/TAR/TAR.GZ/TGZ/GZIP | 只识别容器类型并保存原件 | 不调用 Qwen | `parse_status=skipped`，角色为 `engineering_reference`，安全状态为 `unscanned_archive`，不阻塞 RMA |

图片与 PDF 补充规则：

- 无 `Content-Disposition` 但带 `Content-ID` 的 MIME 图片按 inline 处理；低于配置尺寸/字节阈值的签名、图标等资源写 `skipped_decorative`，不调用 Qwen。
- 文本 PDF 使用本地抽取文本后调用 Qwen 文本模型；扫描 PDF 使用 PyMuPDF 渲染受限页数，再以临时数据输入调用 Qwen VL。
- 预签名 URL 查询串、渲染 data/base64 和附件二进制不得进入任何日志、浏览器控制台或测试快照；文本附件送模后的语义输入允许进入受限 AI JSONL。

2026-07-15 指定样本验收：原始 MIME 共识别 12 个附件，现行链在 OSS 前剔除 7 个装饰 inline 资源，仅创建 5 个业务附件与对应 OSS 对象；原始 EML 仍完整归档。5 个业务附件最终均由 Qwen 解析成功，预规则结果由后续 `email_parse` job 复用，流程终点形成待审核回复草稿。

- 单附件超过 50MB 仍保留 OSS 对象，但不自动解析，写 `needs_manual_review/FILE_TOO_LARGE_FOR_AUTO_PARSE`。
- 工程辅助压缩容器写 `skipped/ENGINEERING_REFERENCE_NOT_REQUIRED` 元数据，`parse_error` 为空；不属于 `unsupported`，不触发人工复核。
- 其他不支持类型仍写 `unsupported/UNSUPPORTED_FILE_TYPE`。
- Qwen 失败仅影响对应附件，保留已抽取文本并转人工；DeepSeek 邮件级解析继续执行。
- Qwen 响应对常见 JSON 形状漂移执行受控归一化；若仍不满足 schema，`ai_call_logs` 与内部 JSONL 保留脱敏后的完整语义请求、原始模型响应和错误分类，便于提示词调优。
- 附件 JSON 固定包含 `file_type`、`summary`、`key_points`、`extracted_fields`、`extracted_items`、`raw_text`、`warnings`、`truncated`。

解析结果状态：

- 规则候选：`candidate_only`
- 待处理：`pending`
- 自动采纳：`auto_applied`
- 人工采纳：`manually_applied`
- 部分采纳：`partially_applied`
- 拒绝：`rejected`
- 需人工：`needs_manual_review`
- 无关自动跳过：`auto_skipped`

异常要点：

- `PARSE_RESULT_NOT_FOUND`
- `PARSE_RESULT_TICKET_NOT_FOUND`
- `PARSE_RESULT_ACTION_INVALID`

测试要点：

- AI 低置信状态。
- AI 不可用转人工。
- 采纳创建工单。
- 拒绝不改写工单字段。
- `field_audit_logs` 写入。

## 16. SN、安全闸门、RMA 与 SQL Server API

- `POST /tickets/{id}/validate-sn`：标准化 SN，校验格式、重复、存在、状态、客户、物料并保存保修证据；失败创建 `sn_validation_failed`。
- `GET /tickets/{id}/export-safety`：只读查看当前完整安全报告，不改变状态。
- `POST /tickets/{id}/validate-export`：先执行或复用新鲜 SN 结果；失败立即停止。全部通过后生成快照/哈希并进入 `ready_for_export`。
- 通用 `/transition` 对 `ready_for_export` 返回 `EXPORT_SAFETY_GATE_REQUIRED`。
- `PATCH /tickets/{id}/owner`：仅 admin 用于负责人纠错，不是正常分配入口。
- `GET /system/integrations/sqlserver/status`：只返回 `disabled/misconfigured/configured` 和缺失项，不返回密码。
- `POST /system/rma-test/preflight`：仅 admin，纯离线生成、解析测试 PDF/MIME；返回精确地址、附件哈希和失败原因，绝不发送。

RMA 任务执行前再次比较 `ticket_version + safety_check_hash + sn_validation_hash`；任一变化都应标记旧任务 `superseded`。RMA 邮件仅允许一个 To，Cc/Bcc 为空，归档 EML 必须含唯一 PDF 附件和对应 `EmailAttachment`。

当前状态机/API 冲突：

- 人工复核不得以 `manual_close` 绕过 RMA 签发闸门；业务取消须设计独立终止状态。
- 合法闭单路径只有 `ready_for_export → rma_sent / rma_reply_sent → closed / rma_issued_and_archived`。SMTP 成功和 Message-ID 是进入 `rma_sent` 的必要条件；进入 `closed` 前，状态机必须从回复、RMA、出站邮件、PDF OSS 对象和附件关联重新核对正式编号、PDF 校验、SMTP Message-ID、PDF/出站 EML 归档等持久化事实，不能只信任调用方布尔参数。
