## §3 邮件中心

### §3.1 IMAP 拉取流程

入口：`app/services/imap_fetcher.py` → `fetch_imap_emails()`

**步骤 1**：创建 `job_run_logs` 记录，`job_type=imap_fetch`，状态 `running`。

**步骤 2**：连接 IMAP（`imaplib.IMAP4_SSL`），选择 `INBOX` 文件夹（只读模式），按 UID 搜索邮件。默认拉取最近 10 封未读邮件（`unseen_only=True`）。

**步骤 3**：对每封邮件：
- 通过 `UID FETCH` 获取原始 EML 字节。
- `payload_from_eml_bytes()` 解析邮件头、正文、HTML、附件、Message-ID、In-Reply-To、References。
- 若 `archive_to_oss=True`：原始 EML 上传 OSS（`source_type=raw_eml`），附件分别上传 OSS（`source_type=email_attachment`）。
- 设置 `payload.imap_uid` 和 `payload.fetch_job_run_id`。

**步骤 4**：调用 `email_service.ingest_email()` 入库。

**去重机制**：通过 `emails.message_id` 字段的 UNIQUE 约束 `uk_emails_message_id` 实现。`ingest_email()` 中先查询 `message_id` 是否已存在，若存在则标记为重复（`duplicate=True`），不重复入库；同时写入 `duplicate_of_email_id` 字段关联到原始邮件。

**步骤 5**：写入 `mail_fetch_records` 拉取记录，记录 `mailbox_account`、`folder_name`、`imap_uid`、`message_id`、`fetch_job_run_id`、`email_id`、`duplicate` 标记和 `fetch_status`。

**步骤 6**：更新 `job_run_logs` 统计数、状态和耗时。单封失败不中断批次（`partial_success`），整个连接失败才标记 `failed`。

### §3.2 邮件入库

入口：`app/services/emails.py` → `ingest_email()`

1. 查询 `message_id` 是否已存在（`uk_emails_message_id` UNIQUE 约束命中），存在则标记重复。
2. 归一化主题，计算 `from_domain`。
3. 写入 `emails` 表，`mail_direction=inbound`。
4. 写入 `email_attachments` 表（关联 OSS 对象）。
5. 写入 `mail_fetch_records` 表（在 `fetch_imap_emails()` 中完成）。
6. 写入 `email_ticket_links` 关联（后续线程归并流程）。
7. 触发自动解析（若 `auto_parse=True`）。

### §3.3 邮件线程

`app/models/mail.py` 中 `EmailThread` 模型：
- `thread_key` 唯一键，用于线程归并。
- `merge_confidence` 和 `merge_reason` 记录归并依据。
- `manual_locked` 防止自动拆分。

API 接口 `POST /api/v1/email-threads/{id}/merge` 和 `/split`，受限操作（`manual_locked=1` 仅 admin 可操作）。

## §4 AI 解析

### §4.1 AI Provider 架构

AI Provider 抽象层位于 `app/integrations/`，支持双 Provider：

| Provider | 文件 | 能力 |
| --- | --- | --- |
| DeepSeekProvider | `ai_provider.py` | `chat_json()` 文本调用，支持 JSON 结构化输出 |
| QwenProvider | `qwen_provider.py` | `chat_json()` 文本调用 + `vl_chat()` 多模态调用（图片/PDF OCR） |

`ai_configured()` 函数（`app/services/ai.py`）支持双 Provider 判断：

```python
def ai_configured() -> bool:
    return (settings.AI_PROVIDER.lower() == "deepseek" and bool(settings.AI_API_KEY)) or \
           (settings.AI_PROVIDER.lower() == "qwen" and bool(settings.QWEN_API_KEY)) or \
           bool(settings.AI_API_KEY)
```

Provider 选择逻辑（`_provider()`）：当 `AI_PROVIDER=qwen` 时使用 `QwenProvider`（API Key: `QWEN_API_KEY`，模型: `QWEN_MODEL`，Base URL: `QWEN_BASE_URL`）；否则回退 `DeepSeekProvider`。

### §4.2 AI 调用重试机制

调用入口 `_run_ai_json()` 实现指数退避重试：

- 最大重试次数：`AI_MAX_RETRIES=2`（共 3 次调用机会）
- 退避策略：`delay = AI_RETRY_BASE_DELAY_SECONDS * (2 ^ attempt)`，即 1.0s → 2.0s
- 可重试错误：TIMEOUT / OUTPUT_NOT_JSON / OUTPUT_SCHEMA_INVALID / HTTP 5xx
- 不可重试错误：HTTP 4xx、其他非临时性错误

### §4.3 解析类型

| parser_type | 说明 |
| --- | --- |
| `rule` | 规则解析（模板匹配、正则提取） |
| `ai` | AI 解析（DeepSeek 或 Qwen 文本调用） |
| `manual` | 人工标注 |

解析结果写入 `parse_results` 表，包含 `intent_type`、`extracted_fields`、`extracted_items`、`missing_fields`、`conflict_fields`、`confidence_score`、`field_confidences`、`evidence`、`apply_status` 等字段。

### §4.4 多模态解析

`parse_attachment_multimodal()` 使用 QwenProvider 的 `vl_chat()` 接口对图片（image/*）和 PDF 附件进行视觉识别，提取 SN、故障描述等结构化信息。前提条件：Qwen API Key 已配置且附件已有可用 OSS URL。

### §4.5 AI 日志

- 数据库 `ai_call_logs`：保存调用摘要（trace_id、call_type、provider_name、model_name、prompt_version、input_summary、output_summary、parsed_key_result、confidence_score、latency_ms、status）。
- JSONL 文件：完整 prompt/input/output 写入 `logs/ai/{yyyy}/{mm}/{dd}/ai-{yyyyMMdd}.jsonl`，每行包含 `trace_id`、`call_type`、`prompt_version`、`input`、`request`、`output`、`parsed`、`latency_ms`、`status`、`error_message`、`created_at`。

## §5 工单与 SN 校验

### §5.1 工单状态机

状态流转由 `workflow_transitions` 表定义，由 `transition_ticket()` 执行。

状态列表：

| 状态码 | 说明 |
| --- | --- |
| `new_email` | 新邮件入库，尚未解析 |
| `parsed` | 已完成解析 |
| `need_customer_info` | 缺失关键信息，需追问客户 |
| `auto_replied` | 已生成/发送追问草稿 |
| `manual_review` | 进入人工复核 |
| `ready_for_export` | 信息完整、可导出 |
| `error` | 系统异常 |
| `closed` | 已关闭 |

主要流转路径：

```text
new_email → parsed → ready_for_export          (信息完整、SN 通过)
new_email → parsed → need_customer_info        (缺字段)
need_customer_info → auto_replied              (生成追问草稿)
auto_replied → parsed                          (客户回复补充)
任意非终态 → manual_review                     (低置信度/SN 异常/冲突/超限)
manual_review → ready_for_export               (人工修正通过)
任意非终态 → error                              (系统异常)
任意非终态 → closed                             (人工关闭)
```

### §5.2 乐观锁

`repair_tickets.version` 字段用于乐观锁：修改工单字段时需传入 `version`，后端比对当前版本，不匹配则返回 `TICKET_VERSION_CONFLICT`。

### §5.3 SN 校验

SN/资产库导入 `sn_assets` 表，板卡规则导入 `board_cards` 表，当前使用 XLSX 格式导入（`/api/v1/master-data/sn-assets/import` 和 `/board-cards/import`）。

校验规则：
- SN 是否存在于 `sn_assets` 库。
- 资产状态是否为有效（`asset_status=valid`）。
- 客户名称/编号是否匹配。
- 物料名称/代码是否匹配。
- 是否需要寄北京（`board_cards` 规则）。

校验结果写入 `sn_validation_results`，不通过时自动创建人工复核任务。

## §6 回复管理

### §6.1 回复草稿生成

入口：`create_reply_draft()` (`app/services/replies.py`)

流程：
1. 推断回复类型（`receipt` / `missing_fields` / `sn_invalid` / `manual_review`）。
2. 检查追问次数，超限则转入 `manual_review`。
3. 选择回复模板，渲染草稿。
4. 尝试 AI 生成更自然的草稿（`generate_ai_reply_draft()`），失败时使用模板草稿。
5. 写入 `reply_records`，`review_status=pending`，`send_status=pending_review`。
6. 创建人工审核任务。
7. 若为首次追问，流转工单状态 `need_customer_info → auto_replied`。

### §6.2 SMTP 发送与收件人白名单

SMTP 收件人白名单实现三层拦截：

**第一层**：`create_reply_draft()` 强制人工审核

生成草稿后，若 `_recipient_in_whitelist(reply.to_addresses)` 返回 `False`，强制设置 `review_status=pending` 并记录警告日志。

**第二层**：`_reply_can_auto_send()` 自动阻断

自动发送条件检查中包含白名单验证：收件人不在此白名单中时，即使 `AUTO_SEND_ENABLED=true` 且 `reply_send_mode=auto_send` 也不会自动发送。

**第三层**：`_send_reply_via_smtp()` 最终拦截

实际 SMTP 发送前再次检查白名单，不在白名单中的收件人直接返回失败："收件人邮箱不在白名单中，开发阶段禁止向真实客户邮箱发信。"

**白名单配置**：`SMTP_RECIPIENT_WHITELIST=["rmatest2@accotest.com"]`（`app/config.py`）。

**SMTP 发送逻辑**：
- 端口 465：SMTP_SSL 直连。
- 端口 587：STARTTLS 升级。
- 发送成功后写入 `smtp_message_id`，归档外发邮件到 `emails` 表（`mail_direction=outbound`），创建 `email_ticket_links` 关联。
- 发送失败则记录 `send_status=send_failed` 并创建人工复核任务。

### §6.3 回复审核

- `approve_reply()`: 人工审核通过，调用 `_send_reply_via_smtp()`。
- `reject_reply()`: 驳回，`send_status=rejected`。
- `update_reply()`: 人工改写草稿内容。

## §9 后台任务

### §9.1 APScheduler 调度

`app/main.py` 在 `lifespan` 中初始化 `AsyncIOScheduler`，注册两个定时 Job：

| Job | ID | 间隔 | 函数 | 说明 |
| --- | --- | --- | --- | --- |
| IMAP 拉取 | `imap_poll` | `IMAP_POLL_INTERVAL_MINUTES`（默认 5 分钟） | `_scheduled_imap_fetch()` | 定期从 IMAP 拉取新邮件 |
| 自动追问 | `auto_followup` | `AUTO_FOLLOWUP_INTERVAL_MINUTES`（默认 5 分钟） | `_scheduled_auto_followup()` | 扫描 `need_customer_info` 状态工单并自动生成追问草稿 |

### §9.2 自动追问逻辑

`_scheduled_auto_followup()` 执行流程：
1. 查询所有 `current_status_code=need_customer_info` 的工单。
2. 跳过追询次数已达上限的工单。
3. 若 `AUTO_SEND_ENABLED=false`，全部跳过。
4. 对每个符合条件的工单调用 `create_reply_draft()`。
5. 日志记录处理数、跳过数、错误数。

### §9.3 其他后台任务

- `fetch_imap_emails()` 也支持 API 手动触发（`POST /api/v1/emails/fetch`）。
- 基础资料导入任务由 API 同步触发，写 `job_run_logs` 审计。
