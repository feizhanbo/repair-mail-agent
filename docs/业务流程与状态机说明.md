## 一、核心业务流程全景

系统从邮件入库到工单关闭的完整链路如下：

```
邮件入库（手工 / IMAP 预留）
  │
  ├─ Message-ID 去重：已存在 → 跳过
  │
  ├─ 线程归并：In-Reply-To 命中 → 归入已有线程
  │              归一化主题匹配 → 归入已有线程
  │              无匹配 → 创建新线程
  │
  ├─ 意图分类（classify_email）
  │   ├─ irrelevant（无关邮件） → parse_status = "skipped"，流程终止
  │   └─ 其他意图 → 继续
  │
  ├─ 规则预解析（reparse_email + extract_fields）
  │   ├─ 正文清洗 clean_email_body()
  │   ├─ 意图再分类
  │   ├─ 正则提取 SN / 邮箱 / 电话 / 故障描述
  │   ├─ 识别缺失字段 missing_fields
  │   └─ 产生 ParseResult（parser_type="rule", apply_status="candidate_only"）
  │
  ├─ LLM 必审解析（所有非无关邮件均触发）
  │   ├─ 构建 Prompt：邮件正文 + 附件 + 规则解析上下文
  │   ├─ 调用 DeepSeek → AiExtractResponse（JSON 结构化输出）
  │   ├─ 输出邮件类型、字段抽取、置信度依据、人工处理方向和原始证据
  │   ├─ 写入 JSONL 日志 + ai_call_logs 摘要索引
  │   └─ 产生 ParseResult（parser_type="ai"）
  │
  ├─ AI 解析结果分流
  │   ├─ 置信度 ≥ 阈值、字段完整、无冲突 → apply_parse_result(auto_applied)
  │   │   ├─ 同线程已有工单 → 关联原工单并更新字段/明细
  │   │   └─ 首次报修 → 创建工单、写状态日志和 EmailTicketLink
  │   ├─ 无关邮件且无需人工 → parse_status="skipped"
  │   └─ AI 不可用/低置信/缺字段/冲突 → 创建或关联 manual_review 工单 + 人工任务
  │
  ├─ SN 校验（手动触发或在 parsed 状态自动）
  │   ├─ SN 不存在 → failed → "manual_review"
  │   ├─ SN 过期/禁用 → failed → "manual_review"
  │   ├─ 客户/物料不匹配 → warning → "manual_review"
  │   └─ 全部通过 + 无缺失字段 → "ready_for_export"
  │
  ├─ 人工复核（manual_review 状态）
  │   ├─ 任务领取/分配
  │   ├─ 字段修正 + 明细编辑（FieldAuditLog 审计）
  │   ├─ 采纳/拒绝解析候选
  │   └─ 完成任务 → 决定下一步流转
  │
  ├─ 回复草稿（信息完整确认或缺失追问）
  │   ├─ 基于模板 + AI 润色
  │   ├─ 写入 reply_records（send_status="pending_review"）
  │   ├─ human_review 模式 → 创建人工确认任务
  │   └─ auto_send 模式且满足安全条件 → 自动发送；否则转人工确认
  │
  └─ 关单 / 导出
      ├─ ready_for_export → closed（导出完成后关闭）
      └─ 任意非终态 → closed（人工关闭）
```

## 二、工单状态机定义

### 2.1 状态码

| 状态码 | 中文名 | 类别 | 终态 | 说明 |
|--------|--------|------|------|------|
| `new_email` | 邮件已入库 | intake | 否 | 邮件归档完成，已创建工单，尚未流转 |
| `parsed` | 已解析 | processing | 否 | 解析结果已采纳到工单 |
| `need_customer_info` | 待客户补充 | waiting | 否 | 缺少关键字段，需要客户补充信息 |
| `auto_replied` | 已自动回复 | waiting | 否 | 已向客户发送补充信息邮件 |
| `manual_review` | 人工复核 | review | 否 | 需人工介入处理 |
| `ready_for_export` | 可导出 | export | 否 | 字段完整且 SN 校验通过 |
| `error` | 异常 | error | 否 | 系统处理异常 |
| `closed` | 已关闭 | terminal | 是 | 工单完成或终止 |

### 2.2 状态流转规则（WorkflowTransitions）

```
                    ┌──────────┐
                    │ new_email │  工单初始状态
                    └────┬─────┘
                         │
          ┌──────────────┼──────────────┐
          │ parse_       │ parse_low_    │ manual_review
          │ completed    │ confidence   │ _required
          ▼              ▼              ▼
    ┌─────────┐   ┌──────────────┐   ┌──────┐
    │ parsed  │   │manual_review │←──│ ...  │
    └────┬────┘   └──────┬───────┘   └──────┘
         │               │
  ┌──────┼──────┐  ┌─────┼─────┬──────┐
  │      │      │  │     │     │      │
  ▼      ▼      ▼  ▼     ▼     ▼      ▼
┌────┐ ┌────┐ ┌──────┐ ┌────┐ ┌──────┐ ┌──────┐
│need│ │rdy │ │manual│ │rdy │ │need  │ │closed│
│cust│ │_for│ │review│ │_for│ │_cust │ │      │
│info│ │exp │ │      │ │exp │ │_info │ │      │
└──┬─┘ └──┬─┘ └──────┘ └────┘ └──────┘ └──────┘
   │      │
   ▼      ▼
┌──────┐ ┌──────┐
│auto  │ │closed│
│replied│ │      │
└──┬───┘ └──────┘
   │
   ▼
┌────────┐
│ parsed │  (客户回复后重新解析)
└────────┘
```

完整流转表：

| 来源状态 | 目标状态 | 触发事件 | 说明 | 需要人工 |
|---------|---------|---------|------|---------|
| `new_email` | `parsed` | `parse_completed` | 解析成功且置信度达标 | 否 |
| `new_email` | `manual_review` | `parse_low_confidence` | 初次解析置信度低于阈值 | 是 |
| `parsed` | `ready_for_export` | `validation_passed` | 字段完整且 SN 校验通过 | 否 |
| `parsed` | `need_customer_info` | `missing_fields_detected` | 关键字段缺失 | 否 |
| `parsed` | `manual_review` | `field_conflict` | 字段冲突/SN 异常 | 是 |
| `need_customer_info` | `auto_replied` | `reply_draft_created` | 补充信息邮件已生成/发送 | 否 |
| `auto_replied` | `parsed` | `customer_reply_received` | 客户回复后重新解析 | 否 |
| `manual_review` | `ready_for_export` | `manual_resolved` | 人工修正且校验通过 | 是 |
| `manual_review` | `parsed` | `manual_resolved` | 人工修正后回到解析态 | 是 |
| `manual_review` | `need_customer_info` | `manual_resolved` | 人工判定需要客户补充 | 是 |
| `error` | `parsed` | `manual_resolved` | 异常修复后人工恢复 | 是 |
| `ready_for_export` | `closed` | `export_completed` | 导出或下游同步完成 | 否 |

**通用兜底流转**（任意非终态均可触发）：

| 目标状态 | 触发事件 | 说明 |
|---------|---------|------|
| `manual_review` | `manual_review_required` | 任意非终态可人工转入复核 |
| `error` | `system_error` | 任意非终态可因系统异常进入 |
| `closed` | `manual_close` | 任意非终态可人工关闭 |

## 三、场景一：标准邮件全自动处理

**前置条件**：客户发送格式规范的报修邮件，正文包含 SN、故障描述、联系方式等信息。

### 流程步骤

```
1. 邮件入库 ingest_email()
   ├─ 去重检查：message_id_hash 不存在，通过
   ├─ 线程归并：无 In-Reply-To，创建新 EmailThread
   ├─ 意图分类：命中"报修"等关键词 → intent_type = "new_repair", confidence = 0.80
   └─ 写入 emails 表，parse_status = "pending"

2. 规则预解析 reparse_email()
   ├─ clean_email_body() → 清洗正文
   ├─ classify_email() → 重新确认意图
   ├─ extract_fields()
   │   ├─ SN 正则：匹配到 2 个 SN → items = [{sn:"FOVI001"}, {sn:"QTMU002"}]
   │   ├─ 邮箱/电话/故障描述全部提取成功
   │   ├─ missing_fields = {} （无缺失）
   │   └─ confidence_score = 0.90 ✓ (≥ 0.7)
   └─ 创建 ParseResult:
       parser_type = "rule"
       apply_status = "candidate_only"
       extracted_items = {"items": [...]}

3. LLM 必审 create_ai_parse_candidate()
   ├─ 构建 Prompt：邮件正文 + 附件文本 + 规则上下文
   ├─ 调用 DeepSeek
   ├─ AI 返回: intent_type="new_repair", extracted_fields={...}
   │            confidence_score=0.90，confidence_reasons=[...]
   └─ 创建 ParseResult(parser_type="ai")

4. AI 结果自动采纳 apply_parse_result(apply_status="auto_applied")
   ├─ ticket_id = None → create_ticket_from_parse_result()
   │   ├─ 创建 RepairTicket
   │   │   ticket_no = "RMA20260707120000000001"
   │   │   current_status_code = "new_email"
   │   │   customer_name / contact_person / problem_description 等已填充
   │   │   missing_fields = {} / conflict_fields = {}
   │   │   confidence_score = 0.90
   │   ├─ 写入 TicketStatusLog (None → new_email)
   │   ├─ 写入 EmailTicketLink (link_type="source")
   │   ├─ 创建 2 条 RepairTicketItem (SN 去重后)
   │   └─ ai_parse_result.apply_status = "auto_applied"
   │
   └─ 状态流转（ticket.current_status_code == "new_email"）
       ├─ confidence_score(0.90) >= 0.7
       └─ transition_ticket("parsed", trigger="parse_completed")
           └─ 写入 TicketStatusLog (new_email → parsed)

5. 无 missing_fields → 不触发 need_customer_info 流转

6. 后续：手动或自动触发 SN 校验
   ├─ validate_ticket_sn()
   │   ├─ SN "FOVI001" → sn_assets 匹配成功，状态 valid，客户/物料匹配 → pass
   │   ├─ SN "QTMU002" → sn_assets 匹配成功 → pass
   │   └─ has_problem = false, has_warning = false
   └─ current_status == "parsed", 无问题无缺失
       └─ transition_ticket("ready_for_export", trigger="validation_passed")
```

### 最终状态
- **工单状态**: `ready_for_export`
- **解析结果**: 1个规则候选 + 1个 AI 解析结果，AI 结果 apply_status = `auto_applied`
- **无需人工介入**

## 四、场景二：低置信度 / 缺字段邮件

**前置条件**：客户发送自由文本邮件，缺少 SN 或故障描述信息。

### 流程步骤

```
1-2. 同上（邮件入库 + 规则解析）

3. 规则解析结果
   ├─ extract_fields()
   │   ├─ SN 正则：无匹配 → sns = []
   │   ├─ 故障描述仅提取到少量文本
   │   ├─ missing_fields = {"sn": "缺少设备 SN。"}
   │   └─ confidence_score = 0.42 ✗ (< 0.7)
   └─ 创建 ParseResult(parser_type="rule"), 置信度低

4. LLM 必审 create_ai_parse_candidate()
   ├─ create_ai_parse_candidate()
   │   ├─ 构建 Prompt：邮件正文 + 附件文本 + 规则上下文
   │   ├─ 调用 DeepSeek
   │   ├─ AI 返回: intent_type="new_repair", extracted_fields={...}
   │   │            confidence_score=0.55（仍低于阈值）
   │   │            manual_review_direction="请核对 SN 和故障描述"
   │   └─ 写入 ai_call_logs + JSONL
   └─ 创建 ParseResult(parser_type="ai")

5. AI 解析不自动采纳（confidence 0.55 < 0.7）
   ├─ ensure_manual_review_ticket_from_parse_result()
   │   ├─ 同线程已有工单 → 关联原工单
   │   └─ 无已有工单 → 创建 manual_review 工单占位
   └─ create_manual_task_if_missing()
       ├─ task_type = "ai_review_required"
       ├─ status = "pending"
       ├─ priority = "normal"
       └─ create_notification() → 全局任务池通知；如已有处理人，再发个人通知
```

### 最终状态
- **工单状态**: `manual_review`，一个复核任务待处理
- **解析结果**: 2个（1个规则 + 1个AI），均为候选待人工确认
- **需要人工介入**：在复核工作台操作

## 五、场景三：SN 校验失败

**前置条件**：工单已处于 `parsed` 状态，但 SN 与资产库不匹配。

### 流程步骤

```
1. 工单当前状态: parsed
   明细行: [{sn: "FOVI001"}, {sn: "INVALID_SN"}]

2. 触发 SN 校验 validate_ticket_sn()
   ├─ 明细行1: sn="FOVI001"
   │   ├─ 查询 sn_assets: 匹配成功，asset_status="valid"
   │   ├─ customer_match = true
   │   ├─ material_match = true
   │   └─ result_status = "pass"
   │
   ├─ 明细行2: sn="INVALID_SN"
   │   ├─ 查询 sn_assets: 无匹配
   │   └─ result_status = "failed", message = "SN 不存在于资产库。"
   │
   ├─ 写入 2 条 SnValidationResult
   └─ has_problem = true

3. 状态流转
   current_status == "parsed" 且 (has_problem or has_warning)
   → transition_ticket("manual_review", trigger="field_conflict")
   → create_manual_task_if_missing()
       ├─ task_type = "field_conflict"
       ├─ priority = "high"
       └─ create_notification()
```

### 最终状态
- **工单状态**: `manual_review`
- **复核任务**: task_type = `field_conflict`, priority = `high`
- **人工需确认**：SN 是否正确，或是否要修改工单明细

## 六、场景四：人工复核闭环

**前置条件**：工单处于 `manual_review` 状态，有一个待处理的复核任务。

### 流程步骤

```
1. 操作员在"人工复核"页面看到任务
   ├─ 筛选 scope="unassigned" → 看到待处理任务
   └─ 任务展示: ticket_no, task_type, priority, trigger_reason

2. 领取任务 claim_task()
   ├─ 校验: task.status in {pending, assigned}
   ├─ task.status = "claimed"
   ├─ task.claimed_by_user_id = 当前用户
   ├─ task.claimed_at = 当前时间
   └─ 写 operation_logs

3. 证据面板查看
   ├─ 邮件原文 + 清洗正文 + HTML
   ├─ 附件（含提取文本和 JSON）
   ├─ 解析候选列表（规则 + AI）
   ├─ 回复链时间线
   └─ 字段审计日志

4. 人工操作（可选，多项可组合）
   ├─ 修改工单字段 patch_ticket_fields()
   │   ├─ 版本号校验（乐观锁）
   │   ├─ 字段值变更
   │   ├─ 写入 FieldAuditLog (source_type="manual")
   │   ├─ ticket.version += 1
   │   └─ 写 operation_logs
   │
   ├─ 修改/新增明细 upsert_ticket_items()
   │   ├─ 更新已有明细字段
   │   ├─ 新增明细行
   │   └─ 写入 FieldAuditLog
   │
   ├─ 采纳/拒绝解析候选
   │   ├─ apply_parse_result(parse_result_id, action="apply")
   │   │   ├─ 工单已存在 → 更新字段 + 追加明细
   │   │   └─ parse_result.apply_status = "manually_applied"
   │   └─ apply_parse_result(parse_result_id, action="reject")
   │       └─ parse_result.apply_status = "rejected"
   │
   └─ SN 校验（重新校验修正后的字段）

5. 完成任务 resolve_task(next_action)
   ├─ task.status = "resolved"
   ├─ task.resolved_by_user_id = 当前用户
   ├─ task.resolved_at = 当前时间
   ├─ task.resolution = 处理备注
   │
   └─ 根据 next_action 执行流转:
       ├─ "transition_ready_for_export"
       │   └─ manual_review → ready_for_export
       │
       ├─ "wait_customer_info"
       │   └─ manual_review → need_customer_info
       │
       ├─ "generate_followup"
       │   ├─ manual_review → need_customer_info
       │   └─ create_reply_draft() → 生成追问草稿
       │       ├─ 基于 reply_template 生成
       │       ├─ 若 AI 可用，调用 AI 润色草稿
       │       ├─ write reply_records (review_status="pending")
       │       └─ create_notification (event_type="reply_waiting_review")
       │
       ├─ "reparse"
       │   └─ reparse_email() → 重新执行规则+AI全流程
       │
       ├─ "close_ticket"
       │   └─ manual_review → closed
       │
       └─ "keep_manual_review"
           └─ 保持在 manual_review，不改状态
```

### 最终状态
- **任务**: `resolved`
- **工单状态**: 取决于 `next_action` 选择
- **审计链完整**: operation_logs + field_audit_logs + ticket_status_logs

## 七、场景五：客户补充回复

**前置条件**：之前已通过 `auto_replied` 发送追问，客户回复了补充信息。

### 流程步骤

```
1. 客户回复邮件入库 ingest_email()
   ├─ classify_email()
   │   ├─ email.in_reply_to 存在 → 命中系统外发邮件
   │   └─ intent_type = "customer_reply", confidence = 0.85
   ├─ _find_thread_for_email()
   │   ├─ In-Reply-To 精确命中上次外发邮件
   │   └─ 归入同一个 EmailThread
   └─ email 入库到同一 thread

2. 规则解析 reparse_email()
   ├─ 解析客户回复中的补充信息
   ├─ 提取可能的新 SN / 补充字段
   └─ 创建 ParseResult

3. 自动采纳 apply_parse_result()
   ├─ 客户之前工单已存在（通过 thread.ticket_id 关联）
   │   → ticket_id 不新建工单，更新现有工单
   ├─ 更新工单字段（非 manual_locked 字段）
   └─ 追加可能的补充明细

4. 状态流转
   当前工单状态 == "auto_replied"
   → transition_ticket("parsed", trigger="customer_reply_received")
   → 继续后续校验流程
```

### 关键规则
- **不重新创建工单**：客户回复合并到原 thread → 原 ticket
- **回复链维护**：系统外发邮件时设置 `In-Reply-To/References`，客户回复时 `in_reply_to` 匹配
- **manual_locked** 字段不会被覆盖

## 八、场景六：追问与回复审核

**前置条件**：工单处于 `need_customer_info` 状态，需要向客户发送追问邮件。

### 流程步骤

```
1. 生成追问草稿 create_reply_draft()
   ├─ 根据 missing_fields 选择 reply_template
   │   ├─ 缺 SN → "sn_invalid_zh"
   │   ├─ 缺报修信息 → "missing_info_zh"
   │   └─ 人工复核中 → "manual_review_notice_zh"
   │
   ├─ 如果有 AI 配置 → generate_ai_reply_draft()
   │   ├─ 调用 DeepSeek 优化模板草稿
   │   └─ AI 返回置信度 ≥ 0.5 → 采用 AI 优化版本
   │       AI 返回置信度 < 0.5 → 回退到模板原文
   │
   ├─ 写入 reply_records
   │   reply_type = "missing_fields" / "sn_invalid" / "manual_review"
   │   review_status = "pending"
   │   send_status = "draft"
   │   followup_round = 当前追问轮次 + 1
   │
   ├─ 创建通知 → supervisor 角色
   └─ 状态流转: need_customer_info → auto_replied

2. 主管审核 approve_reply()
   ├─ 权限检查: 仅 supervisor / admin
   ├─ 写入 review_status = "approved"
   │
   └─ AUTO_SEND_ENABLED 检查:
       ├─ true → SMTP 真实发送
       │   ├─ 设置 In-Reply-To + References 头
       │   ├─ 记录 smtp_message_id
       │   ├─ send_status = "sent"
       │   ├─ 外发邮件入库（emails.mail_direction = "outbound"）
       │   └─ 写入 email_ticket_links (link_type = "outbound")
       │
       └─ false → 仅更新审核状态，不真实发送
           └─ send_status 保持 "draft"

3. 主管驳回 reject_reply()
   ├─ review_status = "rejected"
   └─ 操作员可重新编辑草稿后重新提交审核

4. 追问次数控制
   ├─ 每次追问 ticket.followup_count += 1
   └─ followup_count ≥ max_followup_count(默认3)
       → transition_ticket("manual_review", trigger="followup_limit_exceeded")
       → 创建 ManualReviewTask(task_type="followup_limit")
```

### 最终状态
- **追问草稿**: send_status = "draft"（默认）/ "sent"（AUTO_SEND_ENABLED=true时）
- **工单状态**: `auto_replied`，等待客户回复
- **追问熔断**: 超过 3 次追问自动转人工复核

## 九、场景七：异常与关闭

### 系统异常处理

```
系统异常发生时:
├─ 写入 system_event_logs（event_type, severity, message, stack_trace）
├─ 当前工单状态非终态
│   └─ transition_ticket("error", trigger="system_error")
│       └─ 不自动创建人工任务（error 流转不含 create_manual_task）
└─ 修复后可恢复:
    └─ transition_ticket("parsed", trigger="manual_resolved", require_manual=True)
```

### 工单关闭

```
工单关闭途径:
1. ready_for_export → closed (export_completed)
   └─ 导出或下游同步完成后自动/手动关闭

2. 任意非终态 → closed (manual_close)
   └─ 人工判定工单无需继续处理时关闭

关闭后限制:
├─ transition_ticket() 首先检查 from_status == "closed"
│   └─ 已关闭工单不允许任何状态流转 → 抛出 TICKET_ALREADY_CLOSED
└─ 工单详情仍可查看（审计数据不可变）
```
