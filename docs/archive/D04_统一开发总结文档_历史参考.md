## 2. 开发目标与一期边界

### 2.1 项目定位

邮件报修自动化系统是一套面向内部试运行的邮件报修处理控制台。系统通过邮件归档、回复链归并、规则/附件/AI 解析、SN 校验、追问草稿、人工复核和工单状态机，实现客户邮件报修从收信到可导出的闭环沉淀与可追溯管理。

### 2.2 一期核心目标

- 自动接收报修邮箱邮件，完成 Message-ID 去重、邮件元数据入库、原始 EML 和附件 OSS 归档。
- 识别新报修、客户补充、内部转发、无关邮件和未知邮件。
- 从正文、标准模板、附件和 AI 候选中抽取结构化报修信息。
- 通过 SN/资产库和板卡/物料规则校验 SN、客户、物料和寄送规则。
- 缺少关键信息时生成追问草稿，默认进入人工审核。
- 低置信度、SN 异常、字段冲突、追问超限、线程不确定、系统异常必须进入人工复核。
- 所有工单状态、字段变更、AI 调用、后台任务和人工动作可追溯。
- 前端提供邮件中心、工单中心、人工复核、自动回复审核、基础资料、AI 日志、系统配置和看板。

### 2.3 一期不做

- 不做正式生产高可用、多租户、复杂权限矩阵和外部系统深度集成。
- 不直接接入 SAP/ITSM，下游导出先以 `ready_for_export` 状态作为边界。
- 不引入 Redis、Celery、Prometheus、Node Exporter。
- 不默认真实自动发送邮件，`AUTO_SEND_ENABLED=false` 是一期安全默认值。
- 不把原始 EML、附件二进制、完整 AI prompt 或真实密钥写入数据库或 Git。

## 3. 项目目录结构

项目实际目录以 `repair-mail-agent/` 为准。

```text
repair-mail-agent/
  backend/
    app/
      api/v1/             # REST API 路由
      core/               # 数据库、响应、统一枚举
      models/             # SQLAlchemy ORM
      schemas/            # Pydantic DTO
      services/           # 业务流程层
      repositories/       # 数据访问层
      integrations/       # IMAP/SMTP/OSS/AI 外部集成
      workers/            # APScheduler 或后台任务
      middleware/         # 请求上下文、日志、鉴权等
    alembic/              # 数据库迁移
    tests/                # 后端测试
  frontend/
    src/
      api/                # API client
      layouts/            # 控制台布局
      pages/              # 页面
      routes/             # 路由
      stores/             # Zustand 状态
      types/              # TS 类型
      utils/              # 枚举、状态标签、工具函数
  docker/
    backend.Dockerfile
    frontend.Dockerfile
  nginx/
    default.conf
  docs/
    unified-enums.md
    source-documents.md
    remote-mysql-root-deployment.md
  .github/workflows/
    deploy.yml
  docker-compose.yml
  deploy.sh
  README.md
  AI开发进度与任务跟踪.md
```

后端依赖方向必须保持稳定：

```text
api -> services -> repositories -> models
workers -> services
services -> integrations
services -> observability
models 不依赖 services
repositories 不依赖 api
integrations 不依赖业务 service
```

## 5. 开发规范与底层约束

### 5.1 代码分层

- API 层只做鉴权、参数校验、调用 service、返回 DTO。
- Service 层承载业务流程、状态流转、跨模块编排。
- Repository 层封装数据库访问，禁止 API 层直接写复杂查询。
- Integration 层封装 IMAP、SMTP、OSS、AI 等外部系统。
- Worker 层只调用 service，不复制业务逻辑。

### 5.2 数据库约束

- 一期数据库范围统一为 26 张表，包含日志和审计表，不再使用"23 张业务表"作为验收口径。
- 状态字段统一使用 `VARCHAR`，不使用数据库 `ENUM`。
- `parse_results` 使用 `apply_status` 表达解析结果应用状态。
- `oss_objects.object_key` 统一为 `VARCHAR(640)`。
- `workflow_*` 只管理工单状态机，不承载邮件、附件、回复、任务、通知等所有状态。
- 邮件事实、解析候选、工单当前视图必须分离。
- 状态流转必须写 `ticket_status_logs`；字段修改必须写 `field_audit_logs` 和 `operation_logs`。

### 5.3 安全约束

- 真实密码、邮箱凭据、OSS key、AI key、JWT secret 不得进入 Git。
- `.env`、`.env.*`、`logs/` 必须被 Git 忽略；仅保留 `.env.example`。
- MySQL 不开放公网端口，只允许 Docker 内网、服务器本机和 SSH 隧道访问。
- AI 完整 JSONL 日志不得暴露给前端，前端只展示摘要和定位信息。
