# 邮件报修自动化系统开发进度文档

## 0. 文档定位

本文档是项目当前状态、任务进度、风险和下一步计划的唯一正式记录。Codex 或其他 AI 开发助手每次开始开发任务前，必须阅读本文档，确认当前项目状态和任务上下文。

适用场景：

- 开始一个新开发任务前确认当前阶段。
- 判断某项能力是否已完成、开发中、待开发或阻塞。
- 开发结束后记录实际变更、验证结果和后续建议。
- 代码与文档冲突时记录冲突和处理结论。

何时查阅：

- 每次开发任务开始前必须查阅。
- 每次开发任务结束后必须更新。
- 任务优先级、阻塞项或验收状态变化时必须更新。

维护规则：

- 只记录当前状态和任务，不重复数据库字段、接口细节、业务模板。
- 已完成、开发中、待开发必须分开写。
- 后期计划必须标明“未落地”或“后续目标”，不能混入已完成能力。
- 不记录真实密钥、密码、邮箱凭据、OSS key、AI key。

## 1. 当前阶段

当前阶段：内部试运行闭环硬化。

> 2026-07-13：已完成项目文档治理P0阶段（归档旧文档、合并重复内容、建立精简6文档体系）。

总体结论：

- 基础业务、DeepSeek 邮件级解析、Qwen 附件级解析、IMAP 只读拉取、APScheduler、OSS 上传下载、用户与权限、人工处理、统计分析和运行时配置已完成代码开发及 mock/local 回归。
- 当前项目已经具备以下基础业务闭环：
  1. 手工 JSON、EML 文件或 IMAP 邮件进入统一预检查，重复和高置信无关邮件在 OSS 前跳过。
  2. raw EML 和附件上传 OSS，附件支持 `docx/xlsx/csv/txt/html/image/pdf` 解析。
  3. Qwen 生成附件级 JSON，DeepSeek 汇总正文、规则和附件结果生成邮件级候选。
  4. 高置信且无冲突结果自动应用；低置信、缺字段、冲突、附件/AI 失败进入人工复核。
  5. 工单字段、明细、附件、证据、SN 校验、状态日志、回复草稿和白名单 SMTP 已形成服务层闭环。
  6. 邮件、工单、SN 和板卡资料具备导入导出入口，邮件/工单/复核页面可展示和下载附件。
- 当前最高风险是 OSS 归档失败行为不一致：IMAP 会失败重试，手工和 EML 导入仍会降级入库。真实 OSS/Qwen、远程数据库、浏览器 E2E 和受控邮箱链路也尚未完成整体验收。

## 3. 当前限制与风险

| 优先级 | 问题 | 当前影响 | 建议处理 |
| --- | --- | --- | --- |
| P0 | OSS 失败可降级入库 | 手工/EML 入口可能产生无 raw EML 或无附件 OSS 关联的正式邮件 | 三个入口统一调用批量归档服务，任一上传失败即阻断正式入库 |
| P0 | `archive_to_oss=false` 可绕过归档 | 手动 fetch 参数和调度配置可破坏强制归档规则 | 保留参数兼容但拒绝 false；错误配置时不启动调度 |
| P1 | 真实附件集成未验收 | 七类附件当前主要由 mock 证明，不能确认真实 OSS/Qwen 兼容性 | 使用非敏感小文件逐类真实验证并记录脱敏结果 |
| P1 | 远程数据库一致性未重验 | 最新 ORM/迁移与远程镜像是否一致缺少当前证据 | 仅经 SSH 隧道执行只读 Alembic/schema smoke |
| P1 | 前端 E2E 缺失 | 导入导出、附件展示和角色主路径缺少浏览器回归 | 使用 Playwright 覆盖三角色和核心业务链路 |
| P2 | IMAP 事务与多实例锁不足 | 同批失败隔离和多进程重复执行风险尚未控制 | 每封独立提交并增加调度并发锁 |
| P1 | ORM relationship 缺失 | 对象导航和 selectinload/joinedload 不便 | 按核心关系补充 relationship，不改变现有查询语义 |
| P2 | parser 冲突检测不足 | 规则解析 `conflict_fields` 覆盖不足 | 增加多 SN、格式异常、字段不一致等冲突检测 |
| P2 | 附件 AI retry 不统一 | DeepSeek 已有受控重试，Qwen 附件调用失败直接转人工 | 统一错误分类、退避和可观测字段 |
| P2 | 行级权限未建模 | operator 数据隔离无法严谨实现 | 先设计业务归属字段和规则，不硬编码临时逻辑 |
| P3 | LangGraph 未接入 | AI 工作流编排、checkpoint、节点日志尚未落地 | 按 P0-P3 后期路线推进 |
| P3 | 业务事件模型未落地 | 维修收到、寄出、客户确认等事件无法结构化沉淀 | 后续新增 `ticket_events / business_stage / business_flags` |
| P3 | 前端构建包偏大 | Vite 主包约 1.5MB，影响首次加载 | 路由懒加载和 vendor 分包 |

## 5. 后期 LangGraph 路线

LangGraph 是后期 Agent 工作流开发计划，不属于当前已落地能力。

P0：最小可运行闭环

- 新增 `backend/app/graphs/`。
- 建立 `EmailRepairGraph`。
- 手工入库邮件后可触发 Graph。
- 复用当前 parser、ai、tickets service。
- 返回 `graph_run_id`、执行状态和结果摘要。

P1：核心业务工作流节点

- 邮件加载、正文预处理、规则粗分类、附件识别、AI 全量解析、schema 校验、业务校验、工单动作计划、人工复核判断、回复草稿节点。
- 引入 Conditional Edge，实现业务邮件、无关邮件、低置信、缺字段、冲突、人工复核等路径。
- Graph 不直接改状态，状态流转必须调用 `WorkflowService`。

P2：异常、日志、持久化、人工兜底

- 新增 `graph_runs`、`graph_node_logs`、`langgraph_checkpoints`、`langgraph_checkpoint_writes`。
- 支持节点级日志、耗时、重试次数、错误原因、输入输出摘要。
- 支持人工 interrupt/resume。
- 大文本不进入节点日志，只保存引用。

P3：优化、扩展、多模型适配、监控统计

- Qwen OCR / Qwen VL 多模态节点。
- 节点耗时、成本、失败率统计。
- 批量邮件并发控制。
- 多模型路由和 Prompt 版本管理。

## 当前落地基线

- 邮件入口已调整为“先预检查、后 OSS 归档”：IMAP UID 去重、Message-ID 去重、高置信无关邮件筛选均发生在原始 EML 和附件上传 OSS 之前。
- 明确无关邮件不会创建正式业务邮件，也不会上传原件或附件；`unknown`、低置信、疑似业务邮件继续进入 OSS/入库/人工审核，避免误丢。
- AI 分工固定为 DeepSeek 邮件级文本结构化解析、Qwen 附件级解析；文本型附件先本地抽取，图片/扫描 PDF 使用 Qwen VL；系统状态拆分为 `text_ai_configured` 和 `multimodal_ai_configured`。
- IMAP 定时拉取保留只读策略：默认 `UNSEEN + BODY.PEEK[]`，不标记已读，不移动邮件，单实例调度。
