## 3. 核心状态枚举

### 3.1 工单主状态

| 状态 | 当前含义 |
| --- | --- |
| `new_email` | 邮件和附件已归档，尚未解析 |
| `parsed` | 邮件内容已完成结构化解析 |
| `need_customer_info` | 缺少必要字段，需要客户补充 |
| `auto_replied` | 追问邮件已成功发送，等待客户回复 |
| `manual_review` | 需要人工复核 |
| `ready_for_export` | 工单字段已确认，可以导出或下游同步 |
| `error` | 系统处理失败，等待排查或重试 |
| `closed` | 工单完成或终止 |

当前 `ready_for_export` 的进入条件以统一安全闸门为准：SN 核心校验先通过，再完成联系人、原始客户邮箱、日期、地址、故障、数量、字符串及目标映射检查。客户确认收到维修设备不是其前置条件。

### 3.2 解析应用状态

`parse_results.apply_status` 当前使用：

- `pending`
- `candidate_only`
- `auto_applied`
- `manually_applied`
- `partially_applied`
- `rejected`
- `needs_manual_review`
- `auto_skipped`

### 3.3 邮件解析状态

`emails.parse_status` 当前使用：

- `pending`
- `parsing`
- `parsed`
- `needs_manual`
- `skipped`
- `sent`

### 3.4 人工任务状态

`manual_review_tasks.status` 当前主要使用：

- `pending`
- `assigned`
- `claimed`
- `resolved`
- `closed`

当前开放任务状态：`pending / claimed / assigned`。

### 3.5 回复状态

`reply_records.review_status` 当前主要使用：

- `pending`
- `approved`
- `auto_approved`
- `rejected`

`reply_records.send_status` 当前主要使用：

- `draft`

- `approved_pending_send`

- `auto_sending`

### 4.7 `email_attachments`

用途：邮件附件元数据和解析结果。

字段：

`id`、`email_id`、`oss_object_id`、`file_name`、`content_type`、`file_size`、`file_hash`、`is_inline`、`content_id`、`parse_status`、`extracted_text`、`extracted_json`、`parse_error`、`created_at`。

压缩附件工程资料口径（2026-07-22，无结构迁移）：

- ZIP、RAR、7Z、TAR、TAR.GZ、TGZ、GZIP 复用现有字段，不新增附件角色列。
- `content_type` 保存规范化容器 MIME，`file_size/file_hash/oss_object_id` 保存归档证据。
- `parse_status=skipped`、`parse_error=null`、`extracted_text=null` 表示业务性跳过而非解析失败。
- `extracted_json` 保存 `file_type=archive`、`detected_format`、`attachment_role=engineering_reference`、`business_required=false`、`ai_parse_required=false`、`blocks_ticket_flow=false`、`security_status=unscanned_archive`、`parse_skip_reason=ENGINEERING_REFERENCE_NOT_REQUIRED`、检测告警和分类时间。
- `unscanned_archive` 明确表示当前没有恶意文件扫描能力，不得解释为安全文件；原件仍使用现有私有 OSS 权限和短期签名下载。

索引：

- `idx_email_attachments_email(email_id)`
- `idx_email_attachments_oss(oss_object_id)`
- `idx_email_attachments_hash(file_hash)`
- `idx_email_attachments_content_id(content_id)`
- `idx_email_attachments_parse_status(parse_status)`

## 6. 数据生命周期

邮件：

1. IMAP 邮件先按 `mailbox_account + folder_name + imap_uid` 查询 `mail_fetch_records`，已处理 UID 不再下载原件。
2. 所有入口规范化 Message-ID，并按 `emails.message_id` 和 `emails.source_content_sha256` 去重；缺失 Message-ID 时以 raw EML SHA-256 生成稳定替代值，旧 hash 仍兼容保存在 `raw_headers`。
3. MIME 附件预筛和完整规则候选解析在 OSS 前执行；装饰性图片和高置信无关邮件不写正式 `emails`、`email_attachments` 或对应附件 `oss_objects`。保留附件在此阶段以扩展名、声明 MIME 和魔数识别压缩容器并写入工程辅助分类元数据，但不打开或解压容器。
4. 通过预检后先创建或复用 `oss_objects` 并上传 raw EML 和全部附件；成功后分别关联 `emails.raw_eml_oss_object_id` 和 `email_attachments.oss_object_id`。
5. 部分上传失败时，成功对象作为暂存对象保留并按确定性 object key/hash 在重试中复用，但三个入口均不得创建正式邮件。
6. 正式邮件事务同时写入规则候选 `parse_results`；异步入口在同一事务写 `email_parse` job 并复用该记录，普通业务附件和邮件级 AI 结果随后更新业务表。工程辅助压缩附件保持 `skipped` 终态，不进入模型输入或人工复核判断。同步兼容入口调用同一解析服务。
7. 与工单关联写入 `email_ticket_links`。

工单：

1. 高置信 AI 解析或人工复核可创建工单。
2. 字段变更写 `field_audit_logs`。
3. 状态流转写 `ticket_status_logs`。
4. SN 校验写 `sn_validation_results`。
5. 回复写 `reply_records`，发送成功后出站邮件回写 `emails`。

AI 日志：

1. 每次模型调用写管理员受限 JSONL 明细和 `ai_call_logs` 摘要索引。
2. 只保存键集合、字符数、哈希、关键结果、trace、错误分类、重试和 token usage。
3. JSONL 可保存完整文本 Prompt/Response，但不保存密钥、认证头、签名 URL 查询串、data/base64 或附件二进制；默认保留 30 天。数据库仍只保存摘要。

## 当前数据一致性基线

- `mail_fetch_records` 是 IMAP 拉取幂等边界，`mailbox_account + folder_name + imap_uid` 唯一约束必须保留；已处理 UID 不再 fetch raw、不再上传 OSS、不再入库。
- Message-ID 去重必须发生在 OSS 上传之前；重复邮件不得产生新的 `oss_objects`。
- 高置信无关邮件不写入 `emails`，也不写入 raw EML/附件 OSS 对象；仅在任务审计中记录 `irrelevant_skipped` 摘要。
- 现行硬规则：进入正式入库的邮件必须能追踪成功状态的 `emails.raw_eml_oss_object_id`，每个附件必须能追踪成功状态的 `email_attachments.oss_object_id`；三个入口和 P0 回归测试已执行失败阻断。
- 数据库验收必须覆盖：Alembic head 与目标库一致、35 张业务表、关键索引/外键/视图、Message-ID 与 UID 唯一约束、OSS 引用完整性及超过 24 小时的未引用 OSS 对象只读检查。
- SQL Server 已实现 ODBC SN 精确查询、增量/全量同步检查点和工单安全快照写出；适配器关闭时返回 `disabled` 且不创建实际导出任务。
- `ticket_relay_exports` 的本地幂等维度包含工单 version 和安全快照 hash；但远端表模式默认按 `ticket_no` 查重，发现旧行即返回成功，不执行 UPDATE。生产启用前必须让远端唯一/更新语义与本地版本幂等一致。
