# 邮件报修自动化系统数据库详细设计文档

最后更新时间：2026-07-13

## 0. 文档定位

本文档是数据库结构、字段、约束、索引、枚举和迁移规则的唯一正式详细说明。开发指导文档只保留数据库原则和核心关系，不展开字段。

适用场景：

- 建表、加字段、删字段、改字段类型。
- 新增索引、唯一约束、外键、检查约束。
- 修改工单状态、解析状态、人工任务状态、回复状态等枚举。
- 查询优化、迁移脚本、数据一致性排查。
- 设计 LangGraph、业务事件、行级权限等后续数据库扩展。

何时查阅：

- 任何数据库变更前必须查阅。
- 涉及工单状态流转、解析结果采纳、人工复核、回复、AI 日志、基础资料时必须查阅。
- 发现 ORM、Alembic、实际库、文档不一致时必须查阅并记录冲突。

维护规则：

- 当前事实以 `backend/app/models/*.py`、`backend/alembic/versions/*.py`、`backend/tests/test_models.py` 为准。
- 修改表结构必须同步 ORM、Alembic、测试和本文档。
- 本文档不得记录真实数据库口令或连接串。
- 后续目标表必须明确标注“未落地”。

## 3. 核心状态枚举

### 3.1 工单主状态

| 状态 | 当前含义 |
| --- | --- |
| `new_email` | 邮件和附件已归档，尚未解析 |
| `parsed` | 邮件内容已完成结构化解析 |
| `need_customer_info` | 缺少必要字段，需要客户补充 |
| `auto_replied` | 已生成或发送追问，等待客户回复 |
| `manual_review` | 需要人工复核 |
| `ready_for_export` | 工单字段已确认，可以导出或下游同步 |
| `error` | 系统处理失败，等待排查或重试 |
| `closed` | 工单完成或终止 |

当前 `ready_for_export` 的进入条件以代码为准：字段完整且 SN 校验通过即可进入可导出。客户确认收到维修后设备是后续 `ticket_events` 目标，不是当前硬性前置条件。

### 3.2 解析应用状态

`parse_results.apply_status` 当前使用：

- `pending`
- `candidate_only`
- `auto_applied`
- `manually_applied`
- `partially_applied`
- `rejected`
- `needs_manual_review`
- `auto_skipped`

### 3.3 邮件解析状态

`emails.parse_status` 当前使用：

- `pending`
- `parsing`
- `parsed`
- `needs_manual`
- `skipped`
- `sent`

### 3.4 人工任务状态

`manual_review_tasks.status` 当前主要使用：

- `pending`
- `assigned`
- `claimed`
- `resolved`
- `closed`

当前开放任务状态：`pending / claimed / assigned`。

### 3.5 回复状态

`reply_records.review_status` 当前主要使用：

- `pending`
- `approved`
- `auto_approved`
- `rejected`

`reply_records.send_status` 当前主要使用：

- `draft`
- `pending_review`
- `approved_pending_send`
- `sending`
- `auto_sending`
- `sent`
- `send_failed`
- `rejected`

## 4. 表字段设计

### 4.1 `users`

用途：控制台用户。

字段：

| 字段 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 是 | 自增 | 主键 |
| `username` | VARCHAR(64) | 是 |  | 登录名 |
| `password_hash` | VARCHAR(255) | 是 |  | 密码哈希 |
| `real_name` | VARCHAR(64) | 是 |  | 真实姓名 |
| `email` | VARCHAR(255) | 否 |  | 邮箱 |
| `phone` | VARCHAR(50) | 否 |  | 电话 |
| `department` | VARCHAR(100) | 否 |  | 部门，当前未作为行级权限依据 |
| `status` | VARCHAR(20) | 是 | `active` | 用户状态 |
| `last_login_at` | DATETIME(3) | 否 |  | 最近登录时间 |
| `created_at` | DATETIME(3) | 是 | CURRENT_TIMESTAMP(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 是 | CURRENT_TIMESTAMP(3) | 更新时间 |

约束和索引：

- `uk_users_username(username)`
- `uk_users_email(email)`
- `idx_users_status(status)`

## 6. 数据生命周期

邮件：

1. 收到邮件后按 `message_id` 去重。
2. 邮件正文、头信息、线程关系写入 `emails`。
3. 附件写入 `email_attachments`，后续 OSS 闭环完成后关联 `oss_objects`。
4. 规则和 AI 解析结果写入 `parse_results`。
5. 与工单关联写入 `email_ticket_links`。

工单：

1. 高置信 AI 解析或人工复核可创建工单。
2. 字段变更写 `field_audit_logs`。
3. 状态流转写 `ticket_status_logs`。
4. SN 校验写 `sn_validation_results`。
5. 回复写 `reply_records`，发送成功后出站邮件回写 `emails`。

AI 日志：

1. 每次模型调用写私有 JSONL。
2. 数据库写摘要、关键结果、trace、JSONL 路径和行号。
3. 不保存密钥。

## 2026-07-13 数据一致性基线

- `mail_fetch_records` 是 IMAP 拉取幂等边界，`mailbox_account + folder_name + imap_uid` 唯一约束必须保留；已处理 UID 不再 fetch raw、不再上传 OSS、不再入库。
- Message-ID 去重必须发生在 OSS 上传之前；重复邮件不得产生新的 `oss_objects`。
- 高置信无关邮件不写入 `emails`，也不写入 raw EML/附件 OSS 对象；仅在任务审计中记录 `irrelevant_skipped` 摘要。
- 进入正式入库的邮件必须能追踪 `emails.raw_eml_oss_object_id`，附件必须能追踪 `email_attachments.oss_object_id`；相关 metadata 测试已覆盖。
- 外部中转服务器同步不新增表；本阶段只预留 service/config，占位函数默认返回 `disabled`、`not_configured` 或 `not_implemented`。
